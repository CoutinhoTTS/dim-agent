# 内存快速增长与不释放：分析方案

## 1. 目标与适用范围

针对两个现象：运行期间内存增长极快；工作结束后观察不到释放。分析要回答：

1. 哪个进程、哪类内存在增长？
2. 在相同空闲状态下，哪些存活分配持续增加？
3. 谁持有这些分配，按什么生命周期应该释放，实际在哪一步没有释放？

这是一份 Linux 排查流程，不依赖 `./dev`，不要求把当前运行方式改成开发脚本。优先使用当前安装版本的实际原生可执行文件，在独立 home 中复现；不能用本仓库最新构建代替当前版本后，就声称分析了原问题。

“RSS 不降”是现象，不等于“对象没有释放”。最终需要区分对象滞留、队列积压、原生库缓存、分配器保留空间和其他映射。暂不调整容器、分配器、业务配额或清理策略。

## 2. 执行边界

- 当前运行实例只做进程级只读观察；不停止、不注入、不修改它的配置或 home。
- 复现实验始终显式指定独立 `--home`，不使用产品 home `~/.dimcode`，不删除真实 Session。
- 先记录版本、进程身份与工作负载，再采样。不把 CLI、App Server、Node、MCP 和工具进程的内存混算。
- 不输出环境变量、完整命令行、配置正文、凭据或模型请求。采样只记录大小、数量、时间和调用栈，不增加业务内容日志。
- 数据保存在权限受限的本地目录，不提交 heaptrack 文件、数据库或原始日志。即使不含堆正文，采样仍可能包含本地路径等敏感元数据，分享前审查。
- heaptrack 增加 CPU、内存和磁盘开销，并可能改变积压速度。先测短流程；每轮预先约定内存、磁盘和时长上限，达到上限就正常停止该实验，不等 OOM。
- 不全局降低 `ptrace_scope`。不以 `killall`、`pkill` 等方式停止进程；仅停止自己启动、身份已确认的实验实例。

## 3. 第一阶段：确认增长进程和内存口径

在正常使用时执行，不要求重启当前程序：

```sh
ps -eo pid,ppid,rss,comm --sort=-rss | head -n 30
```

`RSS` 单位为 KiB。根据父子关系和进程名，分别确认终端客户端、App Server、Node 运行时和工具进程；进程名只是线索，不足以唯一确认身份。当前代码中的 daemon 可能显示为 `dimcode-server`，不一定叫 `dim-app-server`。

确认目标后，将下面的 `12345` 替换成实际 PID：

```sh
PID=12345
readlink "/proc/$PID/exe"
ps -p "$PID" -o pid,ppid,lstart,rss,nlwp,comm
cat "/proc/$PID/smaps_rollup"
```

在增长前、增长后和工作结束后各记录一次。重点比较：

| 指标 | 用途 |
| --- | --- |
| RSS / PSS | 进程物理驻留与按比例分摊的共享页；跨进程汇总优先看 PSS |
| Anonymous、Private_Dirty | 判断增长是否主要发生在匿名私有页；它们不是 Rust 堆的同义词 |
| Swap | 避免换出后 RSS 不涨被误判为内存稳定 |
| NLWP | 原生线程数量，不是 Tokio 任务数量 |

如果 Rust 进程稳定而 Node 或工具进程增长，转到对应进程分析，不继续把 Rust 当作唯一目标。`smaps_rollup` 不可读时先确认权限，不通过提权或修改系统安全设置跳过检查。

## 4. 第二阶段：用原版本建立隔离复现

### 4.1 准备工具和实验目录

Linux Mint / Ubuntu 系可以安装：

```sh
sudo apt update
sudo apt install heaptrack heaptrack-gui
```

以下命令中的 `/absolute/path/to/dimcode` 是实际原生二进制的占位符，不是 npm 的 JavaScript 包装器。根据 `/proc/<pid>/exe` 和安装目录确认它；若显示 `(deleted)`，先找回同一版本安装产物，不改用任意其他版本。不要直接对 `npm`、`npx` 或启动脚本采样。

在终端一设置：

```sh
BIN='/absolute/path/to/dimcode'
CASE=$(mktemp -d /tmp/dim-memory.XXXXXX)
umask 077
mkdir -p "$CASE/home/rust" "$CASE/data"
printf 'Experiment directory: %s\n' "$CASE"
"$BIN" --version
sha256sum "$BIN"
heaptrack --version
"$BIN" app-server --help
```

将实验目录、版本、二进制哈希、操作系统、项目 cwd、使用的模型标识、插件是否启用记录在本地笔记中，不记录任何密钥或配置正文。

最后一条用于确认安装版本支持前台 `app-server` 入口。以下命令遵循当前仓库接口；如果安装版本不同，以它的帮助和对应源码为准。没有该入口时，应使用同一发行版本的独立 App Server，不猜隐藏参数。

### 4.2 前台采样 App Server

如果当前是产品配置模式，终端一运行：

```sh
heaptrack -o "$CASE/data/heaptrack.server" \
  "$BIN" app-server \
  --product-home "$CASE/home" \
  --home "$CASE/home/rust" \
  --unix "$CASE/home/rust/daemon.sock" \
  --no-ws
```

保持终端运行，等服务器开始监听。heaptrack 会打印采样文件的实际路径，压缩后缀可能是 `.gz` 或 `.zst`。

如果当前使用显式模型配置，改用下面这一条，不与上一条同时运行：

```sh
heaptrack -o "$CASE/data/heaptrack.server" \
  "$BIN" app-server \
  --model-config '/absolute/path/models.json' \
  --home "$CASE/home/rust" \
  --unix "$CASE/home/rust/daemon.sock" \
  --no-ws
```

模型配置只引用原有安全凭据来源，不在命令中写入密钥。独立 home 的登录、插件和设置不自动继承；需要时通过正常界面单独配置。不复制生产凭据文件，不改变认证或权限以便复现。

### 4.3 使用相同 CLI 连接

终端二设置与终端一相同的 `BIN` 和 `CASE`，并进入发生问题的项目 cwd。产品模式执行：

```sh
"$BIN" --home "$CASE/home" tui
```

配置文件模式执行：

```sh
"$BIN" --home "$CASE/home" \
  --model-config '/absolute/path/models.json' tui
```

两种模式的客户端和服务器必须匹配。客户端的 home 是 `$CASE/home`；服务器的 native home 是其下的 `rust`，不要互换。若连接失败，先检查原终端的启动错误和版本，不让 CLI 静默另起一个未采样的 daemon 后继续实验。

当前接口和 home 关系依据：[App Server 启动](../../crates/dim-app-server/README.md#L11)、[CLI 连接入口](../../crates/dim-cli/src/client.rs#L176)。安装版本的对应实现仍需核对。

### 4.4 不能复现时的处理

- 先核对原版本、模型、插件、并发、输入与输出规模，不先假设问题已经消失。
- 若必须依赖已有历史，需要另行确认一致性备份和脱敏方式。运行中的 SQLite 不能直接复制单个数据库文件；只能使用正常备份机制或停机后的一致副本，并且只在副本上实验，不迁移或改写原库。
- 若必须依赖账户插件，使用原账户构建，不能换公共构建得出等价结论；私人账户实现与凭据不进入本仓库。
- 本轮默认不做运行中注入。`heaptrack -p` 只能记录附加之后的分配，不能追溯已有分配，而且注入与分离存在暂停或崩溃风险；如确有必要，仅在明确同意后的可丢弃实例上使用。

## 5. 第三阶段：固定工作负载和观测点

先跑一次不带 heaptrack 的隔离基线，确认增长在隔离实例也存在；再用相同起始数据和步骤采样。每轮使用新的实验目录；若需要历史，使用同一合法备份的独立副本。不要在上一轮已经增长的实例上声称“从相同基线开始”。

```text
A: startup idle
      |
      v
B: 10 turns finished, idle
      |
      v
C: 10 more turns finished, idle
      |
      v
D: client detached, unload observation
      |
      v
E: graceful daemon shutdown
```

10 轮只是起始规模；增长很快时缩短。尽量固定工具、输出大小和并发，真实模型输出不确定时记录其规模，不能把不等价负载直接作数量比较。

| 观测点 | 操作与目的 |
| --- | --- |
| A | 启动完成、无工作，记录基线 |
| B | 第一组工作全部结束，无模型、工具、审批或脱离工作未结算；记录空闲值 |
| C | 同一 Session 再完成相同一组工作；重点看 C − B 的存活分配增量 |
| C 后观察 | 不新增输入，观察是否还在增长；有后台工作时不能称为真正空闲 |
| D | 退出所有连接该实验 Session 的客户端，观察已安装版本的空闲卸载；断开不等于关闭或已卸载 |
| E | 正常停止实验 daemon，让采样写完 |

D 的等待要覆盖该版本的卸载宽限期和扫描周期。当前仓库默认宽限期为 60 秒且周期扫描；可先观察约 2–3 分钟，但不能仅凭时间断言卸载成功。界面、RPC 调用、脱离任务仍可能阻止卸载。以已有的已加载 Session 统计或卸载日志确认；缺少证据时标记“未确认卸载”，不把该点用于证明卸载后泄漏。语义见[生命周期](../../docs/architecture/rust-agent/lifecycle.md#L152)。

在第三个终端对已确认的实验服务器 PID，在每个观测点执行下面的快照。`CASE` 使用该轮实际目录，`POINT` 依次改为 A、B、C、D；时间用 UTC 方便对齐：

```sh
PID=12345
POINT=A
{
  date -u '+%Y-%m-%dT%H:%M:%SZ'
  ps -p "$PID" -o pid,ppid,lstart,rss,nlwp,comm
  cat "/proc/$PID/smaps_rollup"
} > "$CASE/data/$POINT.memory.txt"
```

实验开始时也记一次时间，便于对应 heaptrack 的相对时间轴。不能把分析器进程或旧 daemon 的 PID 填入这里；每轮核对启动时间，防止 PID 重用。必要时单独记录子进程的同类快照。

完成后只停止这次隔离实例：

```sh
"$BIN" --home "$CASE/home" daemon stop
```

若正常关闭卡住，记录“关闭未完成”，不要把它当作已释放；先保留现场并查卡点。不要用强杀后的最终 `Leaked` 作为正常关闭证据。

## 6. 第四阶段：从增长定位到分配与持有者

### 6.1 先看曲线，再看调用栈

执行 heaptrack 结束时打印的分析命令：

```sh
heaptrack --analyze '/absolute/path/to/heaptrack.server.gz'
```

用实际文件路径替换，不能假定后缀。分析顺序：

1. 对齐 A/B/C/D，确认采样堆与进程匿名页的增长是否同向。
2. 从峰值占用高的分配栈找项目代码；从 `malloc`、`Vec`、`String` 向调用者展开，不把通用分配器当根因。
3. 比较连续空闲阶段的存活量，而不是只比较累计分配次数。GUI 的时间筛选和统计语义以所装版本为准；区间累计分配、区间峰值都不能冒充“区间末存活”。
4. 若所装版本不能给出观测点的存活组成，先用曲线定位增长阶段和少数主要分配栈，再按下一节补热点所有者的数量或容量。没有时间点证据时，不声称已经获得 B → C 的精确分配差异。

**不只看退出时的 `Leaked`。** 运行期间持续滞留、关闭时正常释放的数据，退出泄漏可以为零，仍然能导致长期运行耗尽内存。

### 6.2 有热点后再补持有关系

heaptrack 回答“哪里分配”，通常不回答“现在谁持有”。Rust 没有通用完整的运行时对象图。对贡献最大的少数分配栈，检查它进入哪些容器、任务或共享引用，在哪个正常生命周期边界移除。

| 热点关联位置 | 最小补充证据 |
| --- | --- |
| Timeline / 存储 writer | 热窗口与待写事件数量、最老积压时间、发布与分发位置，工作停止后是否追平 |
| 历史读取 / 请求 | 同时存活的读取、请求和缓存数量；旧结果是否被返回值、缓存或任务保留 |
| Session / branch / 插件代际 | 已加载实例、未结束任务、未释放订阅数量；卸载后是否继续增加 |
| 连接 / 推送 | 实际队列字节和消费进度，客户端断开后资源是否释放 |

这些是候选排查点，不是已发现的缺陷。先用现有状态和日志；不足时只在实际状态所有者处加临时数量、容量或生命周期统计，不添加另一套业务状态或全对象内存框架，不打印正文。`NLWP` 不能替代任务统计，`size_of` 不能代表含堆字段的完整大小，共享 `Arc` 底层数据不能重复计数。

项目约束与工具边界：

- Timeline 的驻留和读取边界见[存储约定](../../docs/architecture/rust-agent/timeline-storage.md#L117)，不要把“历史应持久保存”误解成“历史必须全量常驻”。
- 现有[测量分配器](../../xtask/src/allocation.rs#L12)只覆盖走 Rust 全局分配器的申请字节，不是 RSS，不含 SQLite 自有 C 分配或 Node 堆；可作交叉验证，不能拿差值直接断言碎片。
- 若需隔离恢复、历史读取和卸载路径，可复用 [restore_cost](../../crates/dim-app-server/examples/restore_cost.rs#L10)。它是缩小问题范围的实验，不等于真实产品复现。

### 6.3 符号不足与非 Rust 增长

- 安装产物被 strip 时，原版本的曲线与部分分配栈仍有价值。进一步定位需要同一产物匹配的调试符号，或从准确版本、锁文件和构建配置重新构建同一产品变体。重建后再次确认问题仍然复现；不能拿当前 HEAD 的符号解释另一份二进制。
- 对支持 Cargo profile 覆盖的对应源码构建，可用 `CARGO_PROFILE_RELEASE_DEBUG=1 CARGO_PROFILE_RELEASE_STRIP=none` 保留调试信息，工具链遵循[构建环境](../../docs/architecture/build.md#L3)。账户构建仍由其原构建入口完成。
- heaptrack 主要跟踪被拦截的原生堆申请，不覆盖所有 `mmap`、线程栈和特殊分配器。若 RSS/匿名页持续增长而被跟踪堆不增长，比较目标进程的 `smaps` 映射，必要时再用原生库或分配器的统计细分；不能直接宣布“不是泄漏”。
- 若 Node 是增长进程，改用其 V8 heap snapshot / allocation profile 查 JS 对象及 retaining path，同时比较 `heapUsed`、`external`、`arrayBuffers` 和 RSS。快照可能暂停进程、增加峰值并包含凭据或正文，仅在隔离实例本地采集，不能直接上传。

## 7. 判定与验证

| 证据 | 下一步 |
| --- | --- |
| B、C 存活堆持续增长，任务与队列已结算 | 按主要分配栈查长期持有、缓存增长和清理缺口 |
| 停止输入后仍增长，队列或后台工作尚未停止 | 先找生产者、消费者及阻塞原因，不直接定性为不可达泄漏 |
| 已确认卸载后，同类残留随加载次数增加 | 查 Session 注册、任务、订阅、共享引用和旧代际的释放路径 |
| 存活堆下降，RSS 不降 | 查原生库、映射、分配器保留空间与碎片；保留多个候选解释 |
| 一段预热增长后稳定，重复负载不再抬高基线 | 可能是有界缓存或保留空间，需要确认容量与业务含义 |
| 修复只降低峰值，B → C 增量不变 | 未解决持续滞留，继续查持有与释放路径 |

根因报告必须列出：进程与原版本、复现步骤、A/B/C/D 数据、主要存活分配栈、持有者、预期释放点、实际未释放的原因，以及尚不能解释的内存。不凭一次 RSS 曲线宣布根因。

有证据后只修对应生产者或所有者。复用能触发该生命周期的用户流测试，再重复同一负载比较空闲基线、每轮残留和卸载结果。正常历史或已加载状态本来就可能增加内存，不要求精确回到进程启动值；判定依据是残留是否有明确所有者、边界和规模上限。最后补一次无 heaptrack 复测，确认收益不依赖采样器。

## 8. 删减检查

首轮只保留三项：进程内存快照、同版本隔离复现、一次原生堆采样。不先建设监控平台、全对象大小接口、通用引用图或新事件通道；不先换分配器、删历史或加定时清空。临时计数和 Node 快照只在对应证据缺口出现时使用。

保留独立 home 是为保护真实数据；保留 OS 与堆两种口径是为避免把 RSS 当作对象占用；保留空闲与卸载观测点是为区分合法持有和释放缺口。三者不能删除而仍满足本方案目标。
