# Rust Agent 设计规则

设计时的判断规则；机制与分工见[架构](../README.md)。事件与状态机的原则（只认序号、事件契约与消费规则、状态可恢复、写入前复核、副作用不重放）以[时间总线总纲](time-bus.md)为准，本文不重复。

## 1. 插件与 Capability 有界

新功能是一个插件，按状态归谁拆成若干部分（[ADR 002](../../adr/002-plugin-scope.md)）：

- **Capability 只指 Session 级与分支级的部分**：经 Session 或分支工厂注册到 Agent 实例，生命周期随 Session 或分支。
- **进程级的部分是进程插件，不叫 Capability**：作为 loader 行装载，不进入 Agent 实例。
- **App Server 只负责装配和对外入口**（Rpc、Transport、Agents 等），不放新功能的业务代码。新插件放在各自的 crate，或作为其他语言的插件包，由 App Server 按配置装载。

Capability 实现 rutis `TypedPlugin` 与 runtime `Capability`：`Deps` 声明全部依赖，含只用于装载顺序的依赖，`apply` 从 `Deps` 取得依赖；`apply` 注册服务与订阅，把句柄交给业务状态和回调；取得的资源立即用 `ctx.effect` 登记释放；`apply` 完成即服务与订阅可用，输入消费和后台业务在此之后启动。Capability 经 Session 级或 Timeline 级工厂注册，工厂只捕获配置和实例标识；作用域服务以该作用域的实例键（`SessionScope`/`BranchScope`）提供，依赖方以 `InSession`/`InBranch` 声明注入。Capability 之间的协调通过提交事件、订阅事件或 `Deps` 声明的服务完成。

所有可装配的运行能力和跨插件服务均由 Plugin 提供，包括文件访问、数据库和代码执行。普通模块只作为所属 Plugin 内部的函数、类型与算法实现，不能藏有绕过依赖声明的全局服务、资源或订阅。资源归属是单父树，服务依赖是允许多个上游的无环图；根、校验、失效重载以及唯一事件总线的目标约束见[单树装配](single-tree.md#产品装配约束目标)。

框架按 rutis 0.10.0 设计：使用 `TypeKey` 和 `require` / `require_as` 读取必需服务，使用 `EventKey<E>` 注册和派发事件。EventKey 的类型约束不代替 caps 事件声明（尚未实现，动态事件为 [ADR 001](../../adr/001-harness-foundation.md) 中的 Proposed）或产品授权，严格读取不代替依赖环预检。具体接口统一见[单树合同](single-tree.md#rutis)，不增第二套服务容器、事件总线或生命周期管理器。

## 2. 作用域的含义

三个作用域按"是谁、在做什么"划分，不按大小划分。

| 作用域 | 含义 | 放什么 |
| --- | --- | --- |
| Process | 所有主体共用的东西 | 目录、存储、连接池、跨 Session 的记录 |
| Session | 一个主体（"我"）：身份、交互面与能力 | 工具来源、技能、工作区、连接、配置、权限上限；本 Session 的所有分支共用 |
| 分支 | 这个主体的一条行为线 | 它的 Timeline、由 Timeline 推出的状态、它自己发起的工作 |

同一 Session 的分支是平等、并行、异步的行为线：各自推进、各自结束，互不依赖。父子关系只记录分支历史的来源（继承到哪个切点），不表示控制或结果回报。需要成为另一个主体（不同的身份或能力）时，创建新的 Session，而不是新的分支。

作用域之间只有五种关系：

| 关系 | 方式 |
| --- | --- |
| 分支使用能力 | 分支 Capability 静态注入 Session 或 Process 服务（向外依赖） |
| 能力在某条分支上被使用 | 入口（工具、方法）按调用方的分支 id 路由到该分支的服务 |
| 能力影响分支 | 向一条或多条分支写输入或事件 |
| 分支影响分支 | 只向对方 Timeline 写输入，异步、不等待对方 |
| Session 管理自己的分支 | 分支目录、身份预留、创建与就绪、发布和关闭结算归 Session 的 TimelineTree（[单树装配](single-tree.md)、[TimelineTree](plugins/TimelineTree.md)） |

除此之外没有跨作用域或跨分支的依赖：分支之间不直接调用对方的服务，Session 能力不持有分支的业务状态（由 Timeline 推出的状态、分支自己发起的工作），分支不持有能力。TimelineTree 持有的分支生命周期状态不是分支业务状态，而是 Session 对自己行为线的管理，保留在 Session。一个功能需要多个作用域时，每部分按上表归位（例如能力在 Session，使用时的状态在分支），各部分在同一模块内登记并作为整体描述。

## 3. 正交

加功能是新增 Capability，或扩展该 Capability 自己的行为和状态。需要改动其他 Capability 时，把协调改为事件或 `injects` 声明的服务，由各 Capability 按自己的消费逻辑处理。

一个功能默认完全落在自己的模块内：自己的事件、状态和入口。需要别处的东西时按顺序选择：

1. 使用现有公开契约；
2. 消费已有事件，或向分支写输入（第 2 节的关系）；
3. 以上都不行，向机制所有者提出通用能力：不带该功能的业务含义，其他功能同样可用。

依赖方向从扩展指向核心：核心部件不硬依赖可选插件，需要可选插件的能力时按调用查找，或在它可用时接入；可选插件不可用只影响它自己的功能（[ADR 002 D3](../../adr/002-plugin-scope.md)）。

不为某一个功能改变其他模块的行为。判断标准是这项改动离开当前功能是否仍然成立：契约本身有误或缺少通用能力时，修正其所有者；只为当前功能把别的模块改成特定形状时，不改。

只由本模块消费的事件和状态是私有内容，可按需增加。其他模块必须理解的事件、跨模块服务、协议方法和 wire 字段是公开内容，非必要不新增；新增时写明谁消费它、现有契约为何不够。功能设计文档设"影响面"一节，列出改动的其他模块和新增的公开内容及各自理由，目标为零。

## 4. 通过时间线扩展行为

新增或修改插件、能力、事件时，按以下规则设计；设计文档的“规则检查”一节逐条回答。

1. **要改别的模块拥有的状态，写一条指令事件。** 状态的所有者按序号读到指令后自己决定，把结果写成事件。提出要求的一方不写结果，不通过同步调用替所有者决定。例：`approval/request` 与 `approval/respond`；`input/withdraw` 与 `input/deleted`。指令没有生效时不写结果事件，由调用方的回复说明。不要为“什么都没发生”新增事件。
2. **对象交给下一个模块后不能撤回。** 交接要有明确的事件，例如 `input/applied` 把输入从 InputQueue 交给 Loop。交接前只有原模块能处理；交接后只能用新模块自己的指令，例如 `stop/interrupt`。
3. **before 回调只在写入前同步变换草稿。** 它在提交锁内运行，改完即将写入的草稿就返回；不阻止写入，不等待外部工作，失败时写入原草稿。草稿表达不了时，向事件所有者要一个通用字段。入口只校验格式和权限，功能检查归功能所有者。
4. **核心机制不带业务含义。** Timeline、Dispatcher、before、批次只提供通用能力；写什么事件、事件代表什么由插件决定。核心模块不为某个插件写特殊处理，只按自己公开的事件合同处理事件。
5. **原子批次一起提交，按序逐条派发。** 订阅者按序号处理事件，看不到批次边界。需要一起生效的事实由生产者写在同一批次，起决定作用的事件放在最后。
6. **模型上下文只包含交接后被读取的事件。** 已采用并被消费的输入、工具结果、已采用的提示词才进入上下文。没有经过交接的东西（被删除的输入、被拦下的提交）不会进入上下文，不需要额外过滤。
7. **插件之间只通过公开的事件和服务交互。** 不读别的插件的内部状态，不同步调用别的插件替它做决定，不改别的模块拥有的状态。
8. **基础设施默认不变。** 基础设施指 Timeline（序号、原子批次、提交与发布、before）、Dispatcher、事件信封与格式、装配与生命周期（rutis、loader、Agent 装配）、Session 与分支门面。插件设计以它们的现有契约为前提，在插件自己的事件、状态和流程内求解，不在插件层加端口、检查点或适配器绕过。

   要修改基础设施，需求必须来自基础设施自身，并在基础设施内闭环：
   - 需求能用基础设施自己的职责来说明，不依赖任何功能的业务含义；
   - 实现和验证都在基础设施内完成，不为某个功能设特例。

   达不到闭环的，是功能自己的设计问题，不改基础设施。机制所有者是 dim 运行时。rutis 是外部依赖：设计按它现有的能力求解，不向它提需求。需求写明：
   - 哪个功能被哪条现有规则或合同挡住（引用条目）；
   - 考虑过哪些现有机制，各自为什么不行；
   - 需要的通用能力，不带业务含义；
   - 对序号、批次、中断、重载的影响；
   - 由谁实现，对应哪个 issue。

   已提出的例子：运行时服务按名字暴露给非 Rust 能力（#4）。
9. **只有后续决定要用的事实才进 Timeline。** 给 UI 显示的走 Session 广播通知。进程级状态（标题、Provider 条目、配置）不进 Timeline，通过所有者的类型化写操作修改。这条规则限制新增事件；必需事件上可以带描述性字段。

插件放在哪个作用域、不设接线模块、配置分离、合同语言中立，见 [ADR 002](../../adr/002-plugin-scope.md) 的决策。

## 5. 职责归属

| 职责 | 归属 |
| --- | --- |
| 事件事实与 sequence 分配 | Timeline |
| 事件含义、处理逻辑、写入时机 | Capability |
| Timeline 写入 | Capability，经分支内注册的 `Timeline` 服务 |
| 状态 | 拥有它的 Capability（`StateCell`，外部只读） |
| 异步操作与取消 | 启动它的 Capability |
| 事件处理器内的等待 | Capability 自持任务，登记后返回 |
| 模型、工具、上下文的执行与格式转换 | Capability 定义的宿主端口；审批宿主在 app-server |

Approval 与 Permission 只管 agent 决策引起的动作（工具调用）；按用户或项目配置运行的命令不属于 agent 体系，由该配置自己负责，启用即运行；功能开关是普通配置，与批准无关。

职责放错位置时修正归属方。

## 6. 验证

需求变化时，旧断言按新需求修改或删除，测试跟随实现。日常行为验证用各 crate 的 `crates/*/tests` 与仓库根的 `tests/integration`（跨包扩展、公开流程）。事件格式样本位于 `crates/dim-agent-types/tests/fixtures/`，是冻结的兼容基线：保留原始公开 wire 样本及其来源，不随实现变更更新；契约测试（`crates/dim-agent-types/tests/*_contract.rs`）对这些样本做反序列化与序列化校验，`cargo run -p dim-agent-types --example compat -- --emit` 输出原生 Rust 样本的 v1 wire 形式供对照。对冻结事件结构的扩展须经设计决定，并在契约测试中登记。
