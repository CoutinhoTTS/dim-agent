Rust 版 dimcode 发布 alpha

npm 包名仍是 dimcode。按 dist-tag 分三个通道，每个通道只在自己内部升级。

让 Claude 代办时，使用项目 skill dim-alpha-release（skills/dim-alpha-release/SKILL.md）。它和本页步骤一致，改动时两边要一起更新。

通道规则

版本号npm dist-tag安装 / 升级当前用途
X.Y.Zlatestnpm i -g dimcodeTS 版正式
X.Y.Z-beta.Nbetanpm i -g dimcode@betaTS 版 beta
X.Y.Z-alpha.Nalphanpm i -g dimcode@alphaRust 版

scripts/publish-npm.mjs 按版本号自动选 dist-tag，其他预发布标识（例如 rc）直接拒绝。

alpha 版本号必须低于 npm 上最新的 beta。 已装的 TS 版 beta 会自动升级到所有预发布版本里最高的那个，不区分 alpha 和 beta。所以只要 alpha 版本号高过最新 beta，beta 用户就会被拉到 Rust 版。 publish-npm.mjs 在写入 npm 之前会检查这一点，不满足就停下。 Rust 版从 0.1.0-alpha.0 起步，远低于 TS 版的 0.5.x，所以目前不受影响。

beta 要不要重新发布？

不用。TS 版的发布脚本一直用版本号里的预发布标识作 dist-tag，现有的 0.5.20-beta.0 已经在 beta 上。latest 和 beta 都不受 alpha 发布影响。

只有想去掉上面那条「alpha 必须低于 beta」的限制时，才需要在 TS 仓库改 packages/cli/src/core/upgrade/update-version.ts，让预发布轨道只选同一标识的版本，然后发一版 beta。这个改动只对升级到新 beta 的用户生效，没升级的老版本仍按旧逻辑选。

发布流程

改版本号→PR 合入 main→打 tag→CI 生成 draft Release→检查并发布 Release→发布 npm

原则：npm 上的包只来自 GitHub Release 里 CI 打好的原始 tgz，发布时不重新构建、不重新打包。

  1. 准备分支和版本号 从最新 origin/main 开分支 codex/release-v0.1.0-alpha.0。以下文件的版本必须一致： Cargo.toml 的 [workspace.package]、Cargo.lock 里的 workspace 包、npm/package.json 及 6 个 optionalDependencies、runtime/package.json、runtime/package-lock.json 的两处 version。在仓库根目录运行： 
    VERSION=0.1.0-alpha.0 node --input-type=module -e '
import { readFileSync, writeFileSync } from "node:fs";
const v = process.env.VERSION;
const old = readFileSync("npm/package.json", "utf8").match(/"version": "([^"]+)"/)[1];
const edit = (f, fn) => writeFileSync(f, fn(readFileSync(f, "utf8")));
const json = (f, fn) => edit(f, s => { const d = JSON.parse(s); fn(d); return JSON.stringify(d, null, 2) + "\n"; });
edit("Cargo.toml", s => s.replace(/(\[workspace\.package\]\s+version = ")[^"]+/, `$1${v}`));
edit("npm/package.json", s => s.replaceAll(`"${old}"`, `"${v}"`));
json("runtime/package.json", d => { d.version = v; });
json("runtime/package-lock.json", d => { d.version = v; d.packages[""].version = v; });
'
cargo metadata --format-version 1 > /dev/null
git diff --stat
    应该只改动这 5 个文件：Cargo.toml、Cargo.lock、npm/package.json、runtime/package.json、runtime/package-lock.json。
  2. 提交并合入 main 
    git commit -am "chore: prepare v0.1.0-alpha.0"
git push -u origin HEAD
gh pr create --fill
    等 PR 的 CI 通过后再合并。release 的 preflight 要求 tag 指向的提交已经在 origin/main 上。
  3. 打 tag，触发 release CI 
    git fetch origin
git tag -a v0.1.0-alpha.0 origin/main -m "v0.1.0-alpha.0"
git push origin v0.1.0-alpha.0
gh run watch "$(gh run list --workflow release.yml -L 1 --json databaseId --jq '.[0].databaseId')" --exit-status
    所有 job 都跑在 self-hosted runner 上，需要 macOS ARM64、Linux x64、Windows x64 三类 runner 在线（标签见 release README）。 已有 tag 想重跑时用 gh workflow run release.yml --ref main -f tag=v0.1.0-alpha.0。
  4. 检查 draft Release，然后发布它 带连字符的 tag 会自动标成 prerelease。确认附件一共 15 个：6 个原生包、7 个 npm tgz，外加 release-manifest.json 和 SHA256SUMS。 
    gh release view v0.1.0-alpha.0 --json isDraft,isPrerelease,assets --jq '{isDraft, isPrerelease, count: (.assets|length), names: [.assets[].name]}'
gh release edit v0.1.0-alpha.0 --draft=false
    npm 发布只接受已经发布（非 draft）的 Release。
  5. 发布到 npm（本地执行） .github/workflows/npm-publish.yml.disabled 还没启用，所以目前在本机用同一个脚本发布。它会校验包名、版本、源提交和 sha256，先发 6 个平台包，最后发 dimcode，并全部打上 alpha tag。 
    VERSION=0.1.0-alpha.0
TAG=v$VERSION
rm -rf staging/npm && mkdir -p staging/npm
gh api repos/arcships/dim/releases/tags/$TAG > staging/github-release.json
SHA=$(gh api "repos/arcships/dim/commits/refs%2Ftags%2F$TAG" --jq .sha)
gh release download $TAG --repo arcships/dim --dir staging/npm --pattern '*.tgz' --pattern release-manifest.json

# 只校验，不写 npm
node scripts/publish-npm.mjs staging/npm $VERSION $SHA

npm login --registry https://registry.npmjs.org
node scripts/publish-npm.mjs staging/npm $VERSION $SHA --publish staging/github-release.json
    开了 npm 2FA 的话，每个包都会提示输入 OTP。dimcode-windows-arm64 是新包名，第一次发布时会在你的账号下创建它。
  6. 验证 
    npm view dimcode dist-tags
npm view dimcode-windows-arm64 dist-tags
npm i -g dimcode@alpha && dim --version
    应看到 latest 和 beta 没有变化，alpha 指向 0.1.0-alpha.0。

下一个 alpha

递增最后的数字，例如 0.1.0-alpha.1，然后从第 1 步开始重复。要升 0.1.1-alpha.0 之类的大版本时，先确认它仍低于 npm 上最新的 beta：

npm view dimcode dist-tags.beta

Rust 版还没有自动升级检查，alpha 用户靠重新运行 npm i -g dimcode@alpha 升级。以后加升级检查时，应只在同一个 dist-tag（同一个预发布标识）里选版本。

出错时

  • npm 发布中途失败：原样重跑第 5 步。已经发布且内容完全一致的包会被跳过；内容不同、认证失败或网络错误都会停下，不会覆盖。
  • alpha 版本号高过 beta 被拦：换一个更低的版本号重新走流程。不要去改这条检查。
  • CI 构建失败：在发布分支上修，源码有变化就换新版本号、打新 tag。不要移动已经推送的 tag。
  • 留下不完整的 draft：确认后只删除这个 draft（gh release delete v… --yes，tag 保留），再用 workflow_dispatch 重跑。

完整的发布约束见 docs/release/README.md 和 dim-release skill。
