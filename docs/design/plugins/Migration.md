# Migration plugin 提议

本文提出将当前旧版 CLI／Desktop 数据迁入原生 Dim 的 Migration 插件。作用域为 process，按客户端入口加载，任务完成后卸载；首版提供 CLI 手动命令，两端复用同一插件实现。本文只提出设计，不修改现有插件、输入、上下文或存储契约。

本提议的评审重点是：保留原生消息角色和旧版有效上下文的采用方式；Session 与附件的可恢复提交；宿主临时装载入口；Provider 部分导入与 OAuth 恢复；支持后补导暂缓数据的去重边界。这些跨模块接口须由对应所有者确认，不能当作现有 API。

规则：[设计规则](../../architecture/rust-agent/principles.md)、[插件契约](../plugin-contract.md)、[rutis 用法](../rutis-usage.md)、[ADR 002](../../adr/002-plugin-scope.md)。交付拆分与验证见[实施计划](../../plan/analysis/legacy-migration.md)。

## 1. 已确认目标

- Migration 是独立插件，由 CLI 命令或 Desktop 导入入口按需加载，执行完成并收尾后卸载；不把迁移业务写进 CLI、Desktop 或 App Server 的装配代码。
- CLI 与 Desktop 使用同一个迁移执行实现，各自只负责入口与展示。
- 迁移可重试，有进度，能查明每个对象的结果与失败原因。
- 支持手动触发。自动触发的时机、提示和交互由各客户端的设计决定；本方案不增加自动触发。
- 首个交付提供 CLI 命令，手动完成一次迁移；不包含 Desktop 交互实现。
- 来源限定为当前旧版 CLI 与 Desktop 的已有数据，不泛化为任意历史版本或其他产品导入器。
- Session 的界面逐条还原旧消息；模型保留原生 `user`、`assistant`、`tool_result` 角色与工具调用配对。
- 保留旧版续聊状态：模型采用旧版有效上下文中的摘要与未压缩后缀，排除已回退内容，不默认重新采用全部原文。
- Provider 部分配置不兼容时，导入兼容部分，明确列出未迁移的设置并保留旧数据。
- 设置冲突时保留目标已配置值，只补未配置项，并明确报告冲突。
- 旧 CLI 和 Desktop 的同一共享设置冲突、且目标尚未配置时，以旧 Desktop 为准。
- Provider 或模型失效不阻止 Session 历史导入；客户端打开和续聊时走普通会话的现有逻辑，Migration 不增加模型可用性检查、专门受阻状态或恢复流程。
- 对目标已实现的功能，导入配置统一保留原来的启用／禁用状态，由各功能正常逻辑应用；仍遵守目标已有配置优先及各自来源权限合同。此规则不改变 Migration 自身的触发策略。
- 用户明确保存的长期权限规则在语义可等价映射时迁移，不支持项明确报告；历史单次审批不迁移为目标授权。
- 首版迁移兼容的 OAuth 登录态，包括 Dim 账户、网页登录的模型账户与 MCP OAuth；不兼容项明确报告，由各账户所有者判断兼容性并恢复。
- 目标业务功能尚未实现的数据暂不导入，保留旧版来源，后续功能具备后差量补导；暂缓项不能记为已导入。
- 首版在迁移前要求使用该旧 home 的旧 CLI／Desktop 退出，确认来源停止写入后再读取稳定数据；后续差量导入同样遵守此前置条件。
- 单个对象迁移失败时，记录原因并继续其他独立对象，最终汇总报告，失败项后续可重试；已经完成的结果保留。
- 旧会话已归档而目标客户端不支持归档时，暂缓整个会话，保留旧版，等目标支持归档后差量导入，不作为普通会话显示。
- 历史进入新的 Timeline 时明确表示一次导入，模型知道这些内容来自旧会话；不倒造旧运行时未记录的事件。

## 2. 调查基线

来源基线：旧版 `dim-agent` 源码，提交 `389f80731effbcd7694541eda934fd5dc2f39c9f`。下表路径相对该源码根目录；源码位置不是待迁移的用户数据目录。

数据映射以源码与文档为依据，验证使用一次性旧库和隔离目标，不以用户的现有产品 home 作为实验环境。

| 来源证据，相对旧仓库根目录 | 用途 |
| --- | --- |
| `packages/agent/src/types/storage.ts` | 持久化实体、消息、关系、压缩、队列、任务、Provider 类型 |
| `packages/types/src/content.ts` | 文本、图片、思考、工具调用和工具结果 |
| `packages/cli/src/agent/storage-adapter.ts` | CLI 的物理 SQLite 结构、消息排序与 blob bytes |
| `packages/desktop/packages/electron-main/src/agent/desktop-sqlite-storage-adapter.ts` | Desktop 的物理 SQLite 结构 |
| `packages/cli/src/core/config-manager.ts` | CLI 配置白名单与实际路径 |
| `docs/packages/cli/core/config-manager.md` | 配置来源导航 |
| `docs/architecture/desktop-custom-dimcode-root.md` | Desktop 自定义根、稳定配置文件与版本段 |
| `packages/plugin/src/runtime/plugin-storage.ts` | 插件的全局与 Session 私有状态 |
| `packages/agent/src/session/context-assembly.ts`、`session-history-manager.ts`、`compaction.ts` | 旧版有效上下文与压缩处理 |
| `docs/packages/agent/session/revert-and-fork.md` | 回退、fork 和关系的含义 |
| `packages/cli/src/core/cli-context.ts` | TUI 独立调度库与 Agent host data |

旧 CLI 与 Desktop 的核心会话表采用同一实体模型，分别有存储适配器；Desktop 另有 `schema_migrations`。迁移读取器必须识别实际表结构，不能调用旧适配器的初始化来读数据，因为它们会创建或升级表。TypeScript 类型中出现的字段不代表物理库一定保存了该字段。

### 2.1 路径不是一个数据库文件

- CN 默认旧 home 为 `~/.dimcode/v2`，Global 默认旧 home 为 `~/.dim/v2`；数据库名分别为 `dimcode.sqlite` 和 `dimglobal.sqlite`。
- 两个来源各自迁移，Global 目标保持在 `~/.dim`，CN 目标保持在 `~/.dimcode`，不把两边的数据或配置合并进一个 home。CLI 批量入口的结果与查询路由见[命令合同](../cli-commands.md#migration-interaction)；插件每次只处理调用方传入的一对来源和目标。
- 旧 home 内还包括 `data/`、配置和插件状态。Desktop 可使用自定义容器根，其 `v2` 解析由旧客户端拥有。
- Desktop 的 `<userData>/storage-root.json` 是定位旧根的配置，不是会话数据本身。插件接收客户端已解析的旧 home，不读取或猜测此配置当前指向哪里；CLI 的默认目录选择和显式覆盖由[命令合同](../cli-commands.md#migration-interaction)定义。
- CLI 的调度记录还可能在 `schedule-tui.sqlite`；仅迁移主库会漏掉它。
- 新 CLI 的产品 home 与旧版版本目录含义不同：原生库位于 `<product-home>/rust/dimcode.sqlite`，见 `crates/dim-cli/src/client.rs`。客户端分别解析来源与目标，再交给插件，并拒绝指向同一数据库。

CLI 与 Desktop 可能已经共享同一个旧 home。同一来源通过两个入口迁移不能产生两份会话；来源路径本身也不能充当稳定记录身份。

### 2.2 目标接收能力

是否导入由目标业务功能及其公开合同决定。已有业务功能缺少导入入口时，提出所有者需求；目标业务功能尚未实现时，暂缓相关数据。当前接收能力的代码依据见[实施计划 §6](../../plan/analysis/legacy-migration.md#6-目标接收能力的代码依据)，实施前按实际代码重新核对。

## 3. 数据清单与候选映射

以下列出迁移范围需要覆盖或明确处置的实体。目标业务功能尚未实现时，其数据本次不导入，保留在旧版来源，明确报告暂缓原因，后续差量补导；不为承接这批数据额外实现目标业务功能或占位记录。“保留为历史”只适用于目标已有历史承接能力的内容，不表示恢复了执行能力。实际功能状态由代码与对应设计核对，不能仅凭下表出现某功能就认定其已实现或未实现。导入入口本身需要补充的代码不属于业务功能未实现，不能据此跳过已确认的导入需求。

| 旧数据 | 候选目标与处理 | 需要解决的问题 |
| --- | --- | --- |
| `providers`、`provider_selections` | 复用 Provider 所有者现有显式导入与来源账本 | 受现有严格字段映射、大小限制和不覆盖规则约束 |
| `sessions` 的身份、cwd、标题、时间 | 新 Session、标题元数据及来源映射；原始时间保留为来源时间 | 目标身份生成、创建幂等、历史时间与导入时间如何分开 |
| `status=archived` | 目标客户端不支持归档时，暂缓整个 Session，包括历史与附件，保留旧版，功能具备后差量导入 | 不作为普通会话发布，也不写整会话已导入标记；目标支持归档时按其所有者合同保留状态 |
| tags | 按目标已有标签功能的合同映射，未实现时保留来源并暂缓该数据 | 不因原生标题元数据存在就假称已经支持标签 |
| `session_states` 的模型、设置、模式、权限 | 保留模型引用，设置按字段交给对应配置所有者；未映射内容保留原记录并报告 | Provider/模型失效由普通客户端逻辑处理；旧模式和权限需做等价映射，迁移不擅自替换模型或扩大权限 |
| `messages` | 完整逐条历史；模型采用的消息保留角色和 parts | 按 `orderKey, messageId` 排序，不能按时间戳重排；处理回退、压缩及不完整工具配对 |
| `session_relations` | 保留 Session 到 Session 的历史来源关系 | 旧 `branch` 是不同 Session 的关系，不等于新版 Session 内 Timeline 分支；不据此重建活跃 Collaboration |
| `session_blobs`、`blob_data`、受管文件 | 迁移 bytes 并建立新引用，复用 Session 文件的所有权与清理契约 | blob 既可能在库内，也可能指向文件；不能只复制 metadata 或继续依赖旧绝对路径 |
| `compaction_states` | 原记录保留；有效上下文按 §5 决定 | 旧消息锚点不等于 Timeline sequence；远端 `rawItems` 不是可读摘要 |
| `file_checkpoints`、文件备份、undo/revert 标记 | 目标文件回退功能未实现时暂不导入，保留旧版来源，供功能具备后差量补导 | 新客户端将文件回退列为范围外，不为迁移新增回退功能；用于确定有效会话上下文的回退边界仍按 §5 处理 |
| `queue_items` | 保留未执行输入及其状态供用户识别 | 不作为新输入自动投递；`pending/processing` 不是已发生的对话 |
| `background_tasks`、`workflow_runs`、调度执行记录 | 保留历史结果与可用产物 | 不恢复 PID、等待者、通知投递或运行中工作；不制造新版终态事实 |
| `scheduled_jobs`、独立调度库、Workflow 定义与文件 | 目标功能已实现时按其配置导入合同迁移，保留原启用／禁用状态；未实现时暂缓 | 新启用配置由功能正常逻辑应用，不将旧运行记录恢复成正在执行的工作 |
| `usage_ledger`、run/daily/skill 统计 | 保留旧账本；如展示则标识为导入统计 | 不能伪造成新版的模型请求、费用或 token 测量；聚合表是派生数据 |
| `permission_decisions`、旧信任与审批记忆 | 区分用户明确保存的长期权限规则与历史单次审批：前者等价映射并报告不支持项，后者不迁移为授权；其他信任与配对另按其合同确认 | 不从单次审批、文件根或历史工具结果推导新授权，也不以放宽权限近似旧规则 |
| CLI `config.json`、Desktop `desktop-config.json` | 分别读取，只迁移有明确目标合同的字段 | 客户端偏好与运行配置分开；旧配置不能整体覆盖新配置 |
| `mcp.json`、项目 `.mcp.json`、Skills 设置、exec shell、Hooks、Web、modality 等 | 每种来源按其所有者合同转换或报告未支持 | 同名文件不保证 schema 相同；共享项目来源不复制成另一份权威；执行开关遵守既有设计 |
| Skills 文件及市场内容 | 优先复用现有来源路径，确需搬运时保留用户内容 | 共享 `~/.agents/skills` 不能重复搬运；安装记录不等于插件可运行 |
| `data/plugins/<plugin>/state.json` 与 Session 私有状态 | 仅由理解其 schema 的插件导入；未知状态保留并报告 | 不用通用 JSON 复制声称恢复插件；不运行旧插件来解码 |
| Provider 静态凭据 | 随现有 Provider 导入合同处理 | 错误、进度与报告不能携带凭据 |
| OAuth grants、Dim 登录、网页登录的模型账户与 MCP OAuth | 首版由各账户所有者迁移兼容登录态，不兼容项明确报告，保留原件并遵守目标已有配置优先规则 | 账户所有者须给出登录态兼容与恢复合同；现有静态 Provider 导入排除 OAuth，不能通过简单复制 token 绕过该边界 |
| 远程配对与设备密钥 | 保留原件，迁移范围按对应所有者合同另行确认 | OAuth 登录态的迁移选择不等于恢复设备配对 |
| hold 心跳、socket、锁、PID、临时文件、缓存、日志 | 不恢复为新版运行状态；原来源保留 | 它们不能证明旧工作仍在运行 |
| Desktop 项目、收藏、排序、窗口与其他客户端数据 | 纳入来源盘点，由 Desktop 所有者决定可用映射 | 目前未完成这些客户端字段的逐项映射，不能计入“完整 Desktop 数据迁移”验收 |

### 3.1 已有机制及其边界

- [Provider 导入](../appserver/provider-management.md#6-persistence-existing-sessions-and-migration)已提供逐项 `imported/already_imported/rejected`，保留源数据，不恢复已删除目标，不复制 OAuth grants。实现位于 `crates/dim-app-server/src/provider/legacy.rs`。当前读取限制为每表 1024 条、累计 8 MiB，迁移编排不能掩盖这些限制。
- [Settings](../appserver/settings-service.md)已有按来源读入旧用户配置并转为原生持久化权威的行为。它处理注册来源，不是任意旧版配置的转换器；新迁移命令不得顺带改变现有自动导入策略。
- [sessions](../appserver/sessions-service.md)提供创建、输入、查询等公开操作；稳定 `submissionId` 已支持输入重试去重，但 `launch` 没有调用方提供的创建幂等键，也没有导入历史 API。
- [Session files](../appserver/session-files.md)已有文件所有权与删除、fork 语义。当前单文件 put 限制为 16 MiB，大附件和大型归档必须有明确分块或所有者补充合同。
- [原生存储](../appserver/native-storage-format.md)的格式及其升级范围由存储所有者定义，不是旧 TypeScript 数据导入。Migration 不能绕过格式门禁、向原生表私写旧记录或改写原库。

### 3.2 Provider 导入的讨论边界

现有 Provider 导入能够处理连接地址、兼容的静态凭据、headers、proxy、timeout、模型来源、用户模型、模型覆盖、启停、模型偏好与作用域选择；仍需通过字段校验，不表示任意旧 Provider 都能导入。

| 项目 | 当前合同与待确认范围 |
| --- | --- |
| API key 等静态凭据 | 按凭据类型导入；保留的凭据引用不等于目标已能解析它，需要核对对应凭据来源 |
| 内置 Provider | 只允许向原生初始版本的内置条目导入，并校验定义兼容；用户已经配置的内置条目不能被覆盖 |
| 自定义 Provider | 同 ID 目标已存在时拒绝，不自动改名；改名会牵涉 Session 与模型选择引用，不能仅作为字段冲突处理 |
| 模型列表与偏好 | 区分 bundled/remote 默认模型、用户添加的模型、覆盖与禁用；不得将用户定制丢回默认目录 |
| 默认模型 | 全局选择、工作区选择与 Session 自身选择分别处理；`activeModelId` 只是提示，不能决定全部目标会话的模型 |
| OAuth 与托管账户 | 首版纳入兼容登录态，由各账户所有者恢复并报告不兼容项。当前静态 Provider 导入仍明确排除 OAuth，需落实账户所有者的导入合同，不能复制 token 后宣称可用 |
| 不支持的旧字段 | 本方案要求导入兼容部分，明确列出未迁移设置并保留来源。现有实现遇到非空 `accountUsageSettings`、`retryConfig`、`capabilityDefaults` 等会拒绝整个条目，Provider 所有者须先更新导入合同；Migration 不自行裁字段。部分导入不豁免必要字段校验和凭据、连接、模型之间的有效性检查 |

Provider 配置与引用按映射保存，但其当前可用性不是 Session 历史导入的前置条件。即使 Provider 导入失败或模型已经消失，也照常导入历史并保留原模型引用。客户端切换、打开和续聊该会话时，使用普通会话遇到模型失效的现有逻辑；Migration 不新增可用性预检、专门的受阻状态、提示或替代模型流程。Provider 导入结果仍按其自身合同报告。

### 3.3 设置项的初步对应

这里只确定已找到的对应关系，不把候选项计作已支持。字段语义、显式清除、冲突和更新路径仍按各所有者合同确认。

| 来源设置 | 目标对应与边界 |
| --- | --- |
| CLI `locale`、`tuiMode`、`tuiNotifyOnComplete`、`tuiMouseMode`、`tuiToolDetailsExpanded` | 新 CLI 已读取同名设置；作为优先核对的直接映射项 |
| CLI `themeId` | 有同名目标键，但仍需确认主题 ID 被新主题目录支持；不能只因键相同就报成功 |
| `skills.json` 的 `disabledSkillIds` | 新 Skills 设置有同名字段；必须核对 Skill 身份和来源，复用共享 Skills 目录 |
| `exec-shell.json` | 新执行宿主有同类来源；核对版本、字段及 shell 路径，不直接整体复制 |
| `mcp.json` 与项目 `.mcp.json` | 有对应业务来源；用户级 server 配置保留原启用／禁用状态，由新版 MCP 正常逻辑应用，目标已有配置仍优先。项目启用权遵守既有用户本地配置合同，项目文件保持原来源，不擅自复制为用户配置 |
| 旧 `permissions.json`、默认审批模式、Session 权限与沙箱设置 | 新用户命令规则来源是 `permission.json`，CLI 预设为 `permissionPreset`。长期权限规则按等价语义迁移并报告不支持项；其他模式与沙箱仍逐项映射，不能重命名文件或将旧审批模式直接等同权限预设 |
| `subagentModel`、`assistantModel`、并发设置 | 按对应所有者逐项映射；不能将旧统一辅助模型选择广播给所有新版插件，模型引用保留其身份映射，实际可用性由正常使用流程处理 |
| `prompt-locale.json`、Desktop `customInstructions` 与各类提示词设置 | 与界面 `locale` 分开；明确目标提示词来源和作用域，不能混入摘要或重复叠加指令 |
| Web、Hooks、Scheduler、Workflow、modality、ExternalAgent 等业务配置 | 按插件所有者 schema 转换；缺少目标合同的项报告未支持，不以通用 JSON 复制替代 |
| Desktop 字体、皮肤、快捷键、窗口、通知等界面设置 | 归 Desktop 映射；CLI 首版不把它们写成 CLI 设置。Desktop 的模型、代理、指令等运行配置不能因此一并排除 |
| Desktop 开机启动、存储根切换及其他系统操作设置 | 不与普通外观偏好等同；是否在目标生效由 Desktop 的迁移设计决定 |

本次迁移先在指定来源范围内解析共享设置：旧 CLI 和 Desktop 保存不同值时，以旧 Desktop 为准，不能由文件遍历顺序决定。再逐项与目标比较，保留目标已配置值，只填未配置项，并报告冲突与所用来源。显式 `false`、禁用、空列表和清除不能因为与默认值相同就被视为“未配置”。该来源优先级只处理同一共享设置，不把 Desktop 专属偏好写成 CLI 设置，也不授权覆盖已有目标配置。

### 3.4 待评审的映射边界

下表列出需要核对的目标合同边界。已确定的产品规则以 §1 为准，字段与来源语义由各所有者核实；若发现新的产品取舍，在实施前明确提出。

| 优先级 | 核对项 | 处理依据 |
| --- | --- | --- |
| 1 | 旧工作目录已经移动或不存在 | 确定目录映射与普通客户端打开行为的边界；迁移不擅自替换 cwd |
| 2 | 其他信任与授权设置如何延续 | 长期权限规则已有等价迁移要求；项目信任、配对等仍按各自合同确定范围，不从历史批准推导 |
| 2 | 标签、关系、收藏等元数据 | 核对目标所有者的实际功能与映射；未实现的数据保留旧版、差量补导，归档会话按已确认的整体暂缓规则处理 |
| 2 | 任务、运行记录、文件回退和统计 | 分别决定导入定义、保留历史或暂不支持；不能从旧 running/pending 状态恢复外部执行 |

### 3.5 历史结果与产物的保存

已导入的非归档 Session 持有一份只读 `legacy-history.json`，通过普通
[Session files](../appserver/session-files.md) 保存。内容包括已支持的 Session 时间与模型引用、
消息元数据、压缩记录、有效回退边界、来源关系，以及属于该 Session 的队列、后台任务、
Workflow 运行、调度执行、权限决定和 usage/run/skill 历史。原状态按历史原样保留，
不作为新版执行、审批授权或计量事实写入。没有可导入所属 Session 的记录保留来源并报告暂缓；
daily 聚合不伪装成新版统计。未实现映射的标签、模式、私有设置、权限与文件回退资料
保留旧版来源并报告，不通过这份归档复制进目标。

后台输出与 Workflow 脚本、运行元数据只从明确授权的旧 home 内读取，作为不可执行的
Session 文件复制，归档内保存新文件引用。不存在、无法读取、越出授权根或超过单文件
16 MiB 限制的产物逐项报告，保留原记录。归档本身超过 16 MiB 时，该 Session 明确失败，
不截断历史，也不发布半成品。原始 PID、通知状态和执行代码即使保存在历史资料中也不恢复。

Timeline 通过当前的消息采用记录表达本次导入，另附一条明确排除在模型有效上下文之外的资料链接；
逐条旧消息与旧版摘要、未压缩后缀仍按 §5 处理。资料与其他附件一起完成后才发布 Session，
重试复用所有者回执。删除 Session 与 fork 沿用文件所有权和清理合同。
Migration 任务报告仅保存对象身份、状态与原因，不保存原始会话、队列内容或凭据。

## 4. Session：恢复对话，不倒造运行历史

旧库主要保存消息、配置、关系及部分状态，没有完整 Timeline。消息中的一个 `tool_use` 不能证明新版 Permission、Approval、ToolExecutor 或模型请求曾经发生。

推荐将两种身份分开：

- 新 Timeline 记录“从哪个来源导入了哪些消息”，事件发生时间是本次导入时间。
- 旧 message ID、角色、顺序、时间、parts 和关联作为历史内容保留。模型看到原生角色，客户端按旧消息逐条显示，并标记所属导入操作。

历史工具调用及其结果作为消息内容使用，不调度工具，不重放审批。旧 `thinking` 作为旧记录保留；缺失的 Provider 签名、隐藏推理状态和 continuation token 不能补造。

```text
Session
  [Imported history: legacy Session S, 3 messages]
    User       ...                    [source time]
    Assistant  tool_use(call-1, ...)   [source time]
    Tool       tool_result(call-1, ...) [source time]
  [Import complete]
  User         New request            [native time]
  Assistant    ...                     [native time]
```

这里“一次导入”是用户可感知的逻辑操作，不要求整段历史塞进一个巨大事件。消息需要可分页、可定位，并让后续压缩能在合法消息边界截断。

### 4.1 上下文入口的实际缺口

现有 `InputBlock` 只有 `raw` 文本；`history.rs::render_input` 将它投影为 user message。仅写插件扩展事件不会进入模型上下文；将 transcript 包成文本也不能保留模型角色。仅改 CLI 展示同样不能解决模型角色。

推荐由输入和上下文所有者设计**采用既有消息序列的通用输入能力**：

1. 输入在边界携带最终消息及必要的稳定来源身份，角色与 parts 使用现有消息类型；Migration 负责旧格式转换。
2. 仍经输入采用、消费链路进入模型上下文。上下文所有者只解释通用消息输入，不认识旧表、migration 或旧插件。
3. 导入出处须有模型可见的说明，不能只存在 `structuredContent`、UI 标签或不可读扩展字段中。
4. 复用 `append` 不驱动新回合的语义。历史导入本身不调用模型；下一次正常输入驱动回合时消费导入上下文。已启用功能因配置应用而产生的普通业务执行，按该功能自己的合同处理，不属于历史重放。
5. 客户端与导出根据同一公开历史结构逐条读取，保留消息身份和工具配对；模型请求本身不需要承担 UI metadata。
6. 输入、投影、存储、协议的兼容合同由各自所有者决定，不能把新增枚举分支视为自然兼容。旧冻结 fixtures 不随迁移实现改写。

以上是所有者需求，不是已存在的 API，也不预先确定字段或事件名称。若所有者无法在既有输入契约内闭环，需要先形成运行时自己的设计决定；不能由 Migration 绕开采用链路增加独立的上下文投影。

## 5. 原始历史与有效上下文

逐条还原历史不等于下一次模型请求包含全部旧消息。旧版有回退状态、压缩游标、摘要和远端压缩材料；直接把 `messages` 全表送给模型可能恢复已撤回内容，或使长 Session 超出窗口。

需要分别定义：

| 视图 | 必须保留的内容 |
| --- | --- |
| 用户可读历史 | 旧库仍保存的完整原始消息、旧顺序和来源；被回退或压缩但仍保存的内容可检查，状态明确；已物理删除的内容无法恢复 |
| 首次续聊上下文 | 旧版有效上下文中的摘要与未压缩后缀，后缀保留原生角色和工具配对；不能把已回退内容重新采用 |

采用保留旧版续聊状态的方案：

- 按旧版有效上下文的边界保留已有文本摘要与未压缩后缀；没有发生压缩的会话保留其有效原消息。回退边界同样约束消息和摘要覆盖范围，摘要不能重新带入已回退内容。
- 完整历史用于逐条查看，不因为迁移重新成为模型上下文。摘要明确注明来自旧记录，不伪造新版执行过的压缩事实。
- 模型读取的原消息保留原生角色和工具配对。采用旧摘要不意味着把后缀消息拼成单个文本块。
- 不默认重新采用全部有效原文，不因兼容失败擅自重新压缩或切换模型。

旧 `rawItems` 是 Provider 专用的远端压缩材料；`[remote-compacted]` 占位符不是摘要，不能作为摘要输入模型。需要核对新版 Provider 链路是否支持使用原材料继续会话；不能仅因它不是文本就判定不能迁移。未确认兼容时不能声称已保留续聊状态；确认不支持时明确报告续聊受阻并保留可读历史，不自动改用全部原文。用户选择其他恢复方式的入口另行设计，迁移本身不擅自发起模型调用。

工具配对损坏时同样不能造一个成功结果。历史保留，报告缺失项；能否采用部分上下文以及怎样呈现，须由上下文所有者确定。

## 6. 插件、任务与重试

### 输入、输出与依赖

| 边界 | Migration 自己的合同 |
| --- | --- |
| 请求 | 已解析的绝对旧 home、目标产品 home，以及宿主提供的目标功能上下文；CLI／Desktop 身份本身不改变映射算法 |
| 输出 | 稳定任务身份、当前进度、逐对象及未迁移设置的结果、最终汇总；结果和恢复依据持久化 |
| 输入边界 | 只读来源快照的 schema、记录和受管文件校验；通过后只传递明确类型，不在消费者反复解析旧数据 |
| 目标依赖 | 宿主的受所有权管理的插件生命周期；内容所有者的公开配置、账户、Session 和文件操作；历史经采用输入进入模型上下文。来源、幂等与差量记录由 Migration 拥有 |
| 结果边界 | 对象局部失败可重试，其他独立对象继续；整体存储故障停止本次。暂缓、不支持、冲突与失败不计作完整成功 |

依赖的既有合同见 [Sessions](../appserver/sessions-service.md)、[Provider](../appserver/provider-management.md)、[Settings](../appserver/settings-service.md)、[Session files](../appserver/session-files.md) 和 [pluginFiles](../plugin-contract.md#4-dims-services)。这些链接不是新增迁移操作的声明；缺口集中列在 §7。

结构以一个按需加载的 process Migration 插件开始：它拥有本次跨 Session 的迁移任务、旧数据读取、转换、来源映射及持久化进度，通过所有者公开操作写目标。宿主持有插件的装载生命周期，执行期间保留插件，已接受工作结算、结果持久化和资源收尾后卸载。仅因需要进度或写输入，不新增 Session/branch 接线部件。

```text
CLI manual command          Desktop entry (separate client design)
          \                 /
            host loads Migration
                       |
               Migration plugin
        read / validate / map / checkpoint
             |             |             |
          Provider      Sessions       Other owners
                         |
                 adopted history input
                         |
                      Timeline
```

“独立运行”采用入口驱动的插件生命周期，无需进入正在聊天的 Session，也不要求新增独立迁移进程。CLI 与 Desktop 复用同一插件实现，宿主进程安排沿用各客户端机制，不另建运行时或数据库写入体系。

```text
CLI migration command
  -> load Migration -> run + progress -> save result + settle -> unload -> exit command

Desktop Import action
  -> load Migration -> run + progress -> save result + settle -> unload -> show result
```

Migration 不作为正常启动时常驻的迁移执行器。按需装载不改写用户的长期启用选择；当前 `plugin.enable/disable`（`crates/dim-app-server/src/plugin_manager.rs`）会提交持久化选择，不能用先 enable、完成后 disable 的组合代替本次装载生命周期。入口应复用宿主的受所有权管理的插件装载和卸载机制，具体跨客户端接入点在宿主所有者处核对，不新增接线插件。

### 6.1 最小任务合同

调用方将已解析的旧 home 和目标产品 home 交给插件；默认目录、交互确认和路径覆盖由各客户端入口拥有。首版要求用户先退出使用该旧 home 的旧 CLI／Desktop，停止相关写入，再启动迁移；入口明确展示此前置条件，迁移过程不主动终止旧进程。共享合同至少支持启动、查询结果和取消；重新执行同一迁移请求即可重试，不先增加一套复杂的 repair 命令。

进度包括当前阶段、对象类型、已处理/总数、当前对象和已确认结果。总数尚未扫描完时明确表示未知；不显示虚假的整体百分比。明细区分：已迁移、已迁移无需重复、冲突、暂缓（目标功能未实现）、未支持、失败、已取消；暂缓、失败与未支持不能计作成功。

```text
$ dimcode migration
Source: <resolved-legacy-home>
Target: <client-home>
Stage:  Sessions
Sessions: 12 / 80    Messages: 1840    Files: 31
Result:  10 imported | 1 already imported | 1 failed
Current: source-session-id
^C  Stop after the current commit settles
```

命令拼写是候选界面，尚未加入 CLI 合同。任务返回稳定 ID；中断、断线、插件重载或进程重启后，再次按需加载插件即可查询最后已确认的状态和重试。进度通知允许丢失，最终结果与重试依据必须持久化，查询能力不要求插件在任务完成后常驻。正常完成后 CLI 命令退出，Desktop 保持运行并展示结果。

### 6.2 重试与提交要求

- 首版要求旧客户端退出、来源停止写入后再建立快照，覆盖数据库、附件及配置文件；迁移期间保持此前置条件。读取旧库仍使用只读 SQLite 一致性快照，包含 WAL 中已提交数据，不能仅因旧版退出就只复制主数据库文件。来源检查与异常诊断在读取合同中落实，不以读取旧库为由调用旧适配器初始化或修改源文件。
- 以对象种类、来源稳定身份和内容指纹判断重复与变化；来源路径只用于定位。同一旧 ID 的不同内容报冲突，不静默合并或覆盖目标。
- 暂缓项保留来源身份和暂缓原因，不写已导入标记；目标功能具备后，后续差量运行能够重新尝试这些项，并复用已建立的身份映射。已完成部分按原幂等与目标冲突规则处理。
- 导入完成记录须区分已覆盖的数据范围与尚未迁移部分；不能因整库或某个对象曾导入过，就跳过其中暂缓的数据。Provider 部分导入也不能封死未迁移设置的后续补导。
- 输入可复用稳定 `submissionId`；但它解决不了创建 Session 回复丢失时的重复创建，也解决不了跨文件、元数据和历史的完成边界。
- 每个 Session 是用户可感知的提交单位；内部可按文件和消息分块。未完成对象不能作为完整会话被普通客户端继续使用；完成后历史、附件、身份与来源映射必须一致。
- 成功记录不能只写进度文件再猜测目标是否提交。重试需要能从目标的稳定身份、回执与已提交历史核对结果；其创建和发布合同由 Sessions/SessionStore 所有者提供。
- 保留来源映射的删除信息，重复运行不复活用户在目标主动删除的对象。已成功迁移的对象不因后续一个对象失败而整批回滚。
- 单个对象的数据或转换失败时，记录该对象的结果并继续其他独立对象；已交接的工作先按所有者合同结算，失败对象不作为完整结果发布。最终汇总失败原因及可重试项，不要求用户在每个局部错误处确认。
- 来源整体不可读、目标存储不可写等使后续工作无法继续的故障停止本次执行，保留已完成结果；不把整体故障当作每个对象的局部失败循环重试。
- 取消先停止接收新工作，释放资源并结算已开始的提交，然后记录结果。取消不自动删除已完成对象，也不靠关闭 CLI 推断任务已终止。
- 不覆盖已有目标，不删除、rename 或升级旧来源。不在进度、错误或普通报告中写入凭据和会话正文。

任务账本是 Migration 的 process 数据，不是会话 Timeline。其持久化格式需要自己的版本决定；不用为进度新增 Timeline 事件。是否需要独立的导入完成领域事件，取决于后续是否有业务决定消费它，不能仅为显示新增。

| Agents / Sessions / SessionStore | §6.2；普通 launch 没有创建幂等键，输入去重不能保护 Session 创建与完整发布 | 稳定身份的可恢复创建、未完成对象的可见性与完成提交；通用合同不理解旧 schema。核对已有 prepared creation 后决定最小补充；由所有者立 issue |
| 协议、存储与各客户端历史读取 | §4.1；当前输入、CLI 投影和 Markdown 导出按已有事件形状解释 | 公开历史消息结构、大小/分页和兼容格式决定；旧 reader 显式拒绝不支持内容，逐条展示和导出一致；由所有者立 issue |
| Session 配置、元数据与客户端 | §3；归档、标签和旧关系需要明确目标映射 | 确定元数据保留与展示，不虚构新分支关系。模型失效复用普通会话逻辑，不为 Migration 新增可用性状态或恢复合同 |
| Provider 所有者 | §3.2、§6.2；现有导入遇到不支持字段拒绝整条，来源账本按整条身份去重，不能直接满足部分导入与后续补导 | 在 Provider 自己的合同中定义兼容部分、未迁移字段与覆盖范围的结果，保护必要字段校验、目标用户修改和删除，并作出持久化格式决定；Migration 不自行删字段或私写 Provider 表 |
| 其他配置与文件所有者 | §3；Settings 不是通用转换器，目标默认值不等于显式用户配置，文件 put 有大小限制 | 各自给出可接受字段、显式配置与缺省的区分、冲突和启用语义；大文件支持只在文件所有者内闭环 |
| Dim 账户、模型账户与 MCP OAuth 所有者 | §3；首版要求迁移兼容登录态，现有静态 Provider 导入不处理 OAuth | 各所有者给出登录态兼容判断、目标冲突与恢复操作，明确不兼容结果；Migration 调用其公开操作，不绕过凭据权威或在普通结果中输出登录材料 |
| PluginManager | §1、§3.3；普通启用操作会覆盖目标选择，缺少仅填未配置项的边界 | 由所有者区分显式选择和出厂缺省，只填缺失启停选择并应用正常加载逻辑；保留目标显式启用、禁用和实现选择，不安装缺失插件 |
| 客户端与插件宿主 | §6；入口要求按需加载、执行后卸载，现有 `plugin.enable/disable` 修改长期配置 | 核对并复用受所有权管理的临时插件装载；宿主持有至任务结算和结果保存，再卸载。跨客户端入口不重复迁移业务，不增加常驻迁移控制插件，不要求 rutis 新能力 |

这里不提出 rutis 新能力。上述问题影响采用、分块、恢复或持久化兼容，先由对应所有者按[规则 8](../../architecture/rust-agent/principles.md#4-通过时间线扩展行为)判断是否成立。评审须明确排序、批次、中断和重载边界；本提议不预先分配接口名、格式号或 issue 编号。所有者确认后分别跟踪其合同与验证，未确认前不宣布已有通用接口可直接实现。

| --- | --- |

| §4.3 before | 无 before 回调 |
| §4.4 核心不带业务 | 旧 schema 与转换只在 Migration；上下文需求以通用既有消息采用表达 |
| §4.5 原子批次 | 消息与完成发布的原子边界须由所有者确定；不把分块通知当作提交 |
| §4.6 上下文采用 | 历史通过采用输入进入上下文，扩展事件不直接投影 |
| §4.7 公开交互 | 只依赖公开服务和消息类型；不读取旧插件运行时或目标内部状态 |

| ADR 002 D1 | 迁移任务跨 Session，属于 process；插件只在按需执行期间装载，持久化进度不依赖其常驻；不把任务状态塞进某个用户会话 |

## 9. 消融检查

本方案不需要通用迁移框架、动态 importer 注册表、专用迁移模型、每个实体一个插件、独立事件总线、每条消息伪造一整轮执行事件，也不需要为进度创建一个 Session。

必须保留的结构只有来源读取边界、明确的实体映射、目标所有者的写入接口、来源映射与恢复依据，以及跨客户端共享的结果合同。它们分别保护源数据、语义正确性、状态所有权、重试和一致展示。

实施顺序与验收见[实施计划](../../plan/analysis/legacy-migration.md)。
