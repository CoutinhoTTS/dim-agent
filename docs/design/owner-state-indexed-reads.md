# 状态结果与未处理输入

Status: Draft.
Scope: 状态 owner 的恢复结果、未处理工作与 Timeline 的读写关系。
Issue: [#1320](https://github.com/arcships/dim/issues/1320)。
依据：[查询合同](timeline-property-query.md)、[插件合同](plugin-contract.md)、[ADR 023](../adr/023-context-usage.md)。

## 1. 决定

写入继续使用 append 和既有原子批次，读取继续使用 query。不增加通用状态 CRUD、Reader、恢复协调插件或插件数据库接口。

业务 owner 保存自己的完整恢复结果。结果事实同时列明这次处理的输入身份。Store 用通用反关联成员索引定位尚无处理结果的输入。原事实不必与处理结果同批提交；恢复不能从它们之间的提交间隙推导出“状态已经完整”。

正常状态读取只读有效结果。恢复可以处理真实未完成工作，不能枚举已处理输入、已结束对象或所有候选后再筛选。迁移和显式修复单独报告。

本文规定目标协议；各 owner 的事件和 payload 由自己的设计定义。它不是当前已经存在的持久化合同。

## 2. 三种对象

| 对象 | 谁写 | 内容 |
| --- | --- | --- |
| 业务输入事实 | 原业务生产者 | 输入、消费、配置、工具结果、输出结算等原合同内容。 |
| 恢复结果事实 | 处理它的 owner | 对应版本的完整恢复状态、覆盖位置、这次处理的输入 ID。 |
| 未处理成员索引 | Store | 业务输入中，尚无该 owner 处理结果确认的身份与位置。 |

恢复结果是派生数据，不替代原有必需事实，也不进入模型上下文。Goal 原来的模型可见状态块继续存在；统计结果不变成新的上下文入口。历史和导出保留未知 owner 的结果事实，不执行其中数据。

## 3. 结果中的位置和确认

各 owner 的结果合同含以下语义字段，绑定使用相同拼写：

| 字段 | 含义 |
| --- | --- |
| schema | owner 的恢复状态版本；与数据库格式、RPC 版本分开。 |
| base_through | 本 schema 显式初始化已经处理完的源前缀；后续结果保持该值。 |
| source_through | 已按序处理完的源事实范围上界，不是该结果自身的 Timeline 序号。 |
| source_ids | 本次确认处理的源事实 ID；非累计历史 ID 列表。 |
| previous_result | 上一个已提交结果身份；新分支或首次初始化为 null。 |
| state | 完整恢复状态，或指向该 owner 不可变状态节点的业务身份。 |

结果自己的 id/sequence 仍来自原事件信封。结果可以在 source_through 之后提交。读取源位置 S 的状态，不能把结果提交序号误当成它覆盖的源位置。

首版 schema 分别为 goal/v1、input-queue/v1、prompt-state/v1、context-usage/v1；各 state 只有所属 owner 的一种定义。result_positions 不按业务字段建特殊 getter。

同一 owner 的输入按原位置处理。不能确认一个尚未处理的输入，不能跳过较早未处理输入却声明完整前缀。无业务作用的输入也须有明确确认：可与后面的实际变化合并确认，不重复保存其正文。

一个输入可以被多个 owner 处理；确认关系按结果类型区分。结果没有改变 state 时可复用原状态节点，但 source_ids 仍只记录本次输入。旧 schema 的确认不证明新 schema 已初始化。

## 4. 写入流程

以下是目标业务流程，不是当前装配图：

```text
原事实提交 -> 按序送达 owner
               -> 计算这次变化，准备本次必要输出
               -> 原子批次：[必要输出，恢复结果及 source_ids]
               -> 提交成功后发布 owner 当前结果

批次尚未提交时崩溃 -> 源输入仍在未处理索引
批次已经提交时崩溃 -> 输出和恢复结果同时存在，输入已从索引移除
```

owner 使用自己的顺序任务处理 I/O；handler 登记工作后返回。并发输入在 owner 内按序合并，不创建新的全局队列。恢复结果引用的节点和本次必需终态必须在同一批次，起决定作用的结果放在最后。

owner 自己写出的输入若也属于自己的处理范围，必须在该批次中明确其已被当前状态处理，或者让它作为后续独立输入消费；不能两者都做，也不能靠忽略全部 self-origin 掩盖业务输入。具体归属由 owner 定义。

取消发生在提交前，不发布新结果；已提交后不回滚事实。关闭结算已接受的工作及必需输出，再移除服务。结果写入失败走已有 fault 路径，不把内存状态当成持久成功。

## 5. 恢复和读取

结果查询限定当前分支的本地 opening 之后；Session fork 复制前缀中的旧结果不能直接作为新分支结果。祖先切点的继承状态由 owner 在新分支初始化时显式导入并校验引用。没有 opening 的旧数据走兼容初始化，不由普通读取猜测范围。初始化以后，未处理输入索引只消费本分支新源事实；固定祖先不是后续派发源。

首次创建的空分支可用默认初始状态，不为零工作制造结果循环；第一份持久结果在本地 opening 后提交。带复制/继承前缀的分支须先按 owner 合同初始化，不能因本地尚无新输入就误认为状态为空。

1. 固定恢复源截止 S；在 owner 开始实时处理之前取得查询读头 H，H 不小于 S。
2. 在 H 内用类型与位置索引取得最后一个兼容且覆盖位置不超过 S 的恢复结果；不解码旧结果正文。
3. 通过 H 对应的成员索引，限定源位置 `base_through < sequence <= S`，取得尚未由该 owner 确认的源输入，按位置处理；读完一页释放一页。
4. 结算恢复状态中明确记录的欠写义务，提交新结果与必需输出；返回源截止 S，交接 S 之后的实时输入。仍在等待未来业务条件的工作保留在 state，不重做已经成功的外部效果。

第 3 步处理的是没有完成的工作，不是把整个后缀从数据库读出来再查确认。其读取量随未完成数 U 增长；U=0 时不读取旧源事件。结果索引、成员索引或状态节点损坏不静默退回完整重放。

S 限制源输入，H 限制结果和确认的可见范围，两者不能混用。实现仍调用一次固定 through=H 的 query，在外层条件限定源位置不超过 S，内层确认使用完整 H。完成一批后取得新 H，重新查询剩余成员；旧游标不能拿到新 H 续用。普通 pending 则仍以原 through 同时限制开始和终态，不采用这条处理确认规则。

普通 get 不执行第 3 步：它等待 owner 已接受的处理完成，或者按原业务合同返回未就绪；不能把未就绪结果伪装成空队列、零 usage 或没有 Goal。首次装载的恢复先完成，才发布相应服务的就绪状态。查询取消不撤销已经提交的工作。

等待只针对本次固定范围内、会影响返回值的工作，不等待未来轮次或持续产生的新输入。恢复结果中的长期业务义务不等于一次 getter 必须等待的 I/O。

Goal get 和 usage 当前读取只要求当前结果；不增加任意历史状态版本接口。pending 保留其原 through 合同，直接使用指定位置的成员集合版本。请求准备所需统计位置由 ContextUsage 明确定义，不能以任意较新统计替代。

## 6. 通用索引要求

存储执行见[成员索引设计](appserver/timeline-member-index.md)。恢复输入的逻辑查询形状仍是现有 query 可表达的反关联：

```text
源类型及公开属性条件
AND NOT EXISTS (
  本 owner、兼容 schema 的恢复结果
  AND Any(source_ids, 当前元素 = 外层源事件 ID)
)
```

source_ids 是本次源 ID 数组，不是恢复时才构建的历史确认集合。索引需要支持数组关联键；不能每次解析全部旧结果的 source_ids，也不能先读所有源输入。

源身份页首版最多 128 项，先取 id、kind、position 及该 owner 实际需要的控制字段。实时送达直接使用已有类型化事件；恢复页只对实际需要内容的成员按 ID 取正文。Goal 不因收到普通输入就取 user/blocks 正文；InputQueue 解释缺 mode 时可按该 ID 做 user 存在性查询，不能返回整份 user 只为判断存在。

128 限制身份数量，不是正文大小上限。大正文逐对象消费并释放，不能把一页 128 份大输出一起收集后再算；计算成本还包括这些真实工作所需的新内容字节。

结果 latest、previous_result 身份、源输入身份及确认关系都必须有可定位的索引。索引只理解查询中声明的类型、属性、数组元素和等值关系，不解释 state。支持的 owner 输入形状须在格式设计中列明，不能把插件内存状态或任意可执行回调交给 Store。

## 7. 初始化与协议边界

旧数据没有这种结果及确认索引，需要一次显式初始化。初始化产生固定截止位置的恢复结果，并按索引构建合同登记该前缀已经处理；不把所有历史 ID 填入一个无限大的 source_ids。失败不标记初始化完成。

先检查最新 owner 结果的 schema。只有明确支持升级的旧版本才初始化；未知版本或较新版本返回不兼容，不跳过它去使用更旧的结果。缺失、已知旧版本、损坏和未知版本不是同一分支。

初始化结果以 base_through 标明基线。它只在旧库初始化、首次启用 owner 或恢复版本升级时建立，不是日常确认前缀的捷径；不得跳过真正未完成输入。查询显式排除这个前缀，不能让索引返回不符合反关联表达式的结果。索引可以保留旧前缀的身份，但必须按外层位置条件直接跳过，不读取它们。初始化结果和它引用的节点原子提交，普通读取不得代建索引。

若 Store 尚未实现该 owner 的源成员索引、数组确认关系和源位置范围定位，该 owner 仍不能声称已实现无历史扫描恢复；不能仅写结果事实后保留“快照 + 全后缀重放”的旧行为。

## 8. 成本、验收和删减

一个最小流程：最后结果覆盖 99，input/message 位于 100。处理成功后同批写 applied 和 recovered，后者确认 ID 100。崩溃发生在批次提交前，索引仍返回 100；发生在提交后，恢复直接取新状态，不再写 applied。若另一个源输入 101 已在该批次前提交，仍留在成员索引，不能因结果自己的序号更大就跳过它。

| 路径 | 允许的工作 |
| --- | --- |
| 已就绪 get | 一个结果定位和实际返回字段；不读源历史。 |
| 无未完成输入的恢复 | 一个结果定位、空成员集合确认、当前状态节点。 |
| 有 U 条未完成输入的恢复 | 索引定位及 U 条实际工作，不访问已确认源正文。 |
| 普通变化 | 新内容/受影响状态计算，必要输出和一次合并结果；不复制历史。 |

扩大已处理历史十倍，保持当前状态和 U 不变，读取量不能线性增长。验证输出与结果之间崩溃、结果提交后回调丢失、重复恢复、并发追加、取消及 owner 未安装/版本升级。source_ids 的增长只与本次工作量有关。

去掉单独的完成标记事件：确认直接随恢复结果提交。去掉通用状态存储服务：结果及节点走原事实批次。保留成员索引是为了直接找到未完成工作，保留结果状态是为了不重做已经完成的业务计算。新增写入和结果保留体积必须单列，不声称恢复性能没有写入代价。
