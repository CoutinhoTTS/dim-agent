# 冷恢复：校验、owner 恢复与读取成本

Status: Draft.
Scope: native store 的完整性校验与产品恢复的分阶段验收。
相关问题：[#1320](https://github.com/arcships/dim/issues/1320)、[#601](https://github.com/arcships/dim/issues/601)、[#713](https://github.com/arcships/dim/issues/713)。
本文补充[校验复用](restore-validation.md)和[冷 attach](cold-attach-profile.md)的成本分析，不改变首次校验、Session 发布或持久化格式合同。

## 1. 各种读取为什么存在

| 阶段 | 必须得到的结果 | 成本归属 |
| --- | --- | --- |
| 存储校验 | 各记录和引用满足存储合同，目录与事件关系完整 | 存储 owner；全量检查每条记录需要扫描。 |
| 业务恢复 | 各 owner 当前状态与必须结算的旧工作 | 对应业务 owner，不能归入存储解码。 |
| 装配和 opening | 必需部件可用、资源启动和 opening 收据完成 | 实际部件；MCP/skills/外部 I/O 等待单列。 |
| 历史显示和 usage | 客户端请求的窗口与统计 | 各自接口，不属于完整性校验的当然成本。 |

attach 总时间不能直接等于逐事件解码时间，更不能把它全部归因于一次 SQL 或一次 fold。

## 2. 校验的 I/O 设计

保持同进程且 Session 目录未变时的现有校验复用，首次打开仍完整验证。读取分批进行，只持有本批正文及跨批次检查必需状态；事件 ID 去重集合等随历史增长的状态单独计量，不能漏出“每页 64 行”的内存报告。

优化仅针对重复工作：尽可能一次解析完成所需边界检查和类型校验；引用及关系检查在等价前提下批量执行。减少解析不能删掉记录格式、序号、批次、引用、分支或压缩边界的检查。

不新增长期完整事件缓存，也不为让第二个业务读复用正文而把整个校验前缀留下。业务恢复应使用自己真正需要的对象。

完整扫描是这里明确接受的业务要求。若要改成延迟或抽样校验，应另作决定，不能作为本设计中的无声优化。

## 3. 测量与验收

产品装配下给 acquire/restore、校验读取/解码/关系检查、Session/branch 装配、各 owner 恢复、opening 和 branch/resume 分别计时。客户端另记录 attach 等待、首个显示请求、投影与首帧、inventories 和 usage。

复用现有进程日志/测量机制，不新增 Timeline 诊断事实或记录用户正文。记录数量与字节、SQL 次数、CPU 与 wall time；区分存储等待、外部服务等待和计算。

用可丢弃的约 1k/5k/12k 事件样本及不同正文大小，分别执行首次打开、同进程卸载再恢复、进程重启和坏库场景。验证复用命中、失败后清除与所有既有拒绝行为。

不把不同进程、不同缓存状态、不同阶段的样本相加。单项优化通过以后，以端到端首帧确认实际收益；不把单项解析基准当产品恢复耗时。

## 4. 边界与删减

本设计不新增插件、Capability、服务、快照或业务数据表，不产生上下文内容。使用既有存储资源与 Session 生命周期；无新的跨模块依赖或格式决定。查询取消释放本次读取，不能返回半份验证结果作为成功。

存储负责可归因的必要完整性工作；其它 owner 的额外遍历由其设计解决。保留已有小型验证目录记录是为了复用已证明的结果，不扩展成正文缓存。
