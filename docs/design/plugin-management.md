# 插件管理：目标与待定义的需求

状态：需求定义草案，不是设计。本文写插件管理要达到什么目的、已经定下的方向，以及还要分析的问题；需求定下来之后，再修订或重写 [PluginManager](plugins/PluginManager.md) 等设计文档。现有机制只给出入口链接。

## 目的

用户和 agent 能快速创作插件、装上就能用，并且 Dim 自身的每一部分都可以被插件配置或替换。

- **凡是 rutis 写的插件都可以替换**，包括 Session 等内核部分和各个 Capability，不只是可选插件。产品侧决定哪些不允许替换；这是产品配置，不是插件机制本身的限制。
- 内置插件尽量可以通过配置替换，能热替换的就热替换。

插件有两类内容：

- **Dim 插件**：以 rutis 部件运行在 Dim 里的插件（Rust、TypeScript 或其他语言），注册工具、提示词来源、方法、服务，参与 Session 和分支。
- **Hooks 等内容型插件**：以 hooks、skills、MCP 配置等内容为主，由 Dim 里已有的所有者插件（Hooks、SkillsCatalog、Mcp 等）读取后生效。

## 已定的方向

| 方面 | 方向 |
| --- | --- |
| 格式 | 使用 Dim 自己的格式。与 Claude Code、Codex 等外部格式的兼容由外部去做，Dim 不读取对方的文件 |
| 安装 | 支持本地（文件）和远程（Git）；市场以后再建。插件管理不增加作用域、审批、信任等额外约束 |
| 约束 | 插件管理对插件不做限制。需要约束时，由已经在运行的插件自己施加（例如 Permission 对工具调用的决定） |
| 更新确认 | 更新需要用户确认，但这是交互界面的事情；App Server 只提供操作 |
| 默认启用 | 由默认配置文件决定 |
| 做成的标准 | agent 或用户能快速写出一个插件并热加载使用；必须重启才能生效的情况（例如 dylib）就重启。内置插件可以通过配置替换或热替换，产品侧约束哪些不能替换 |

## 还要分析的问题

1. **用户眼里是一个“插件”概念还是两个？** 先要弄清 Hooks 这类内容型插件的交互过程（见 [Hooks](plugins/Hooks.md) §3）：它的内容由已有的所有者插件读取，本身不带可执行部件。据此再决定两类插件是否走同一套安装、启用和列表。
2. **生命周期。** 安装、启用、禁用、更新、移除、替换各自对正在运行的 Session 和分支有什么影响；哪些可以热加载、哪些必须重启；替换内核部分（例如 Session）时，已经在运行的实例怎样处理。
3. **替换的含义。** “替换一个内置插件”在配置上怎样表达；产品侧怎样声明哪些不能替换。
4. **快速创作。** agent 或用户从写下一个插件到用上它，要经过哪些步骤；热加载需要宿主提供什么。
