状态：[#170](https://github.com/arcships/dim/issues/170) 的研究结果。本文评估 [ContextCompaction](../plugins/ContextCompaction.md) §13 的两个选择；决定记录在那里（§10、§13.2、§13.3）。英文版：
[English](../../../design/research/summary-eval.md)（以英文版为准）。本文每个数字背后的逐次运行记录在 [`xtask/summary-eval/runs/2026-10-28/`](../../../../xtask/summary-eval/runs/2026-10-28/)。

每条结论都标明证据类型：

- **[实测]**：由评估运行测得，方法见 §2。
- **[代码]**：读自本仓库。
- **[判断]**：本文的推理或推断，未经验证。

## 1. 结论

| # | 问题 | 决定 | 证据 |
| --- | --- | --- | --- |
| 1 | 摘要请求的推理 | `off` | §3：`off` 在测得的推理类上通过且没有质量损失（`F` 0.972 对 0.958，`X` 1.000 对 0.958，`V` 0，无失败） |
| 2 | 是否引入设置 | 不引入：`off` 是策略常量，并移除 `compaction.json` | §3.4：`off` 在这些用例上通过了非劣检验，且没有别的分组的 `F` 比它高出 `δ` 以上 |
| 3 | 目标长度指令 | 不写指令 | §4：第二阶段每个分组都通过，且无指令分组的截断与失败不高于任何目标分组 |

规则与 `δ = 0.05` 出自 §13.4。决定在跑过的那一类（OpenAI 兼容）上做出，对 §13.4 要求的其他每一类都是暂定的：OpenAI Responses 类未能运行（§2.3），本次评估里没有 Anthropic 预算式思考类的模型（§2.1），无推理对照是同一模型的另一个端点，它的第 1 阶段计入、第 2 阶段不计入。

## 2. 方法

### 2.1 类别、模型与评判

| 类别 | 端点 | 结果 |
| --- | --- | --- |
| OpenAI 兼容（按强度的推理） | OpenAI 兼容 | 运行（第 1、2 阶段） |
| OpenAI Responses（按强度的推理） | OpenAI Responses | **未能运行**（§2.3） |
| Anthropic 预算式思考 | Anthropic | **未运行**：本次评估里没有这一类的模型 |
| 无推理对照 | 同一模型的 Anthropic 兼容端点 | 第 1 阶段运行并计入；第 2 阶段不可用（§4.2） |

[实测] 模型是 DeepSeek v4.1 flash，推理强度 max，经它的 OpenAI 兼容端点。它的目录条目声明窗口 1,048,576 token、最大输出 8,192。对话保存的偏好是推理强度 `max`，`inherit` 分组沿用了它（§2.4）。

[实测] 评判是同一族的同一模型，对所有类别（含对照）都跑在 OpenAI 兼容端点上，温度 0、推理强度 `max`（§2.5）。它只看摘要和探针列表，从不看记录。评判与摘要同族是本次评估的局限（§9）。

[实测] 对照是同一模型经它的 Anthropic 兼容端点，请求的强度不产生思考：三个分组发出三种请求形态（`inherit` 不声明，`off` 用原生 `none` 强度、由映射转成关闭思考的声明，`low` 用 `low` 强度），第 1 阶段全部 161 条已记录回复在三种取值下都没有思考。

[实测] Anthropic 预算式思考类未运行：评估只用了 DeepSeek 模型，其中没有这一类的模型。直接发给 Anthropic 兼容端点的探针说明了为什么这个模型不能顶替它：带 `thinking: {"type": "enabled"}` 时端点返回带占位签名（并非真实签名）的思考块，而带 `thinking: {"type": "disabled"}`、或者只给 `low`/`max` 强度而不声明思考时，它完全不返回思考。单独给强度在那里产生不了思考：只有当请求显式声明思考时它才出现。三个分组都不声明，所以在那里从不唤起思考，也就度量不了会思考的摘要器。默认值对预算式思考模型有什么代价或收益，因此没有测过。

### 2.2 用例与指标

[实测] 运行器（§13.4）提交的八个用例，含五步 `chain`，每个用例每个分组运行三次。`F` 是 `fact` 探针的事实召回，`X` 是 `exact` 探针的精确召回，`V` 是 `absent` 探针的违规数，`C` 是停在 `max_tokens` 的回复数，`T` 是摘要的估计 token 数，`S` 是目标分组的目标长度。决定规则（含 `δ = 0.05`）出自 §13.4。

### 2.3 OpenAI Responses 类未能运行

[代码] 请求构造要求原生的推理续接数据（`include: ["reasoning.encrypted_content"]`，`crates/dim-agent-aimux/src/request/native.rs:233-234`），强度不为 `none` 时还要求推理摘要。[实测] 20 条已记录回复中 19 条带推理摘要，0 条带加密内容。[代码] 回复读取器让任何思考部分缺少该续接数据的已结束回复失败（`crates/dim-agent-aimux/src/stream.rs:261-273`），所以 `inherit` 分组的 19 条已记录运行中 18 条以 “Model thinking is missing native continuation metadata” 失败；唯一完成的那次是回复里没有推理的那次。因此这一类度量的是端点与驱动的组合，而不是摘要质量，它的任何分组都不进入决定。等它能运行时，规则在该类上重跑。

### 2.4 记录与运行器缺陷

[实测] 端点前的直通记录器保存了运行器发出的每个请求和每条回复，写入前删除凭据。这从运行器自己的请求证明每类运行之前 `inherit` 沿用了 `max`：OpenAI 兼容类的第一条摘要请求带 `reasoning_effort: "max"`，Responses 类的带 `reasoning: {"effort": "max", "summary": "detailed"}`，对照的既不带 `thinking` 也不带 `output_config`；每次运行的诊断都记录 `reasoning: "inherit"`。

运行器的两个缺陷已在 [#545](https://github.com/arcships/dim/pull/545) 修正：对话与评判配置用了默认偏好而不是模型保存的偏好；`exact` 探针与转义后的摘要比较，低估了 `X`。本处的每个 `X` 都按修正后的规则：先用生产方的转义表（`&`、`<`、`>`）转义探针文本，两边都做空白规范化，再与按原样保存的摘要比较。已保存的摘要按这条规则重算过；在这些运行上，它与最初取值时用的一层反转义完全一致，逐条 `exact` 探针都没有差异。每次运行的摘要原文与它的 `exact` 判定（记录值与修正值）都在 [`xtask/summary-eval/runs/2026-10-28/`](../../../../xtask/summary-eval/runs/2026-10-28/)。

### 2.5 评判与各分组的配置

已记录的各次运行早于 §13.4 现在要求的每次运行记录，所以这里的仪器配置从现存的两处记录重建：隔离评估 home 保存的偏好，以及直通记录器看到的请求字段。

- **保存的偏好。** home 为模型保存了 `reasoningEffort: max`，对话与评判的选择都从它构建（§2.4）。
- **评判。** 它记录在案的 313 条请求每条都带 `reasoning_effort: "max"` 与 `temperature: 0.0`。没有一条在发出去时丢掉温度，所以没有评判请求回退到不设温度；也没有一条带服务层级。
- **各分组。** `inherit` 带对话自己的推理：OpenAI 兼容端点上 `reasoning_effort: "max"`，Responses 端点上 `reasoning: {"effort": "max", "summary": "detailed"}`，Anthropic 兼容端点上什么都不声明。`off` 以模型的关闭声明代替强度：OpenAI 兼容端点上 `enable_thinking: false`，Anthropic 兼容端点上 `thinking: {"type": "disabled"}`。`low` 带 `reasoning_effort: "low"`，在 Anthropic 兼容端点上则是 `output_config: {"effort": "low"}`。第 2 阶段全程用 `off`。
- **服务层级。** 记录在案的 1091 条请求——所有分组的摘要请求与评判请求——没有一条带服务层级，所以每次运行都用提供方的默认层级。那个默认是什么无法从记录中还原，是 §13.4 的记录里本次评估唯一说不出的一项。

这些是记录器在线路上看到的字段：每个请求携带了什么，而不是模型如何处理它。

[实测] 在这些分母上，`δ = 0.05` 相当于 3.6 个 `F` 探针（分母 72）和 1.2 个 `X` 探针（分母 24）：一个 `F` 探针是 0.014，一个 `X` 探针是 0.042。规则能看见约四个 `F` 探针或两个 `X` 探针的损失，看不到更细的差别，所以任一方向上一个探针的差异都落在它视为“无差别”的范围内。

### 3.2 对照类

[实测] 同一规则，在无思考端点上：

| 分组 | 回退 | F | X | V | C | 失败 | T 中位数 | 耗时中位数 ms |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| `inherit` | 0 | 69/72 = 0.958 | 24/24 = 1.000 | 0（原始 1） | 0 | 0 | 442 | 1,433 |
| `off` | 0 | 72/72 = 1.000 | 23/24 = 0.958 | 0（原始 1） | 0 | 0 | 446 | 1,446 |
| `low` | 0 | 71/72 = 0.986 | 24/24 = 1.000 | 0（原始 2） | 0 | 0 | 427 | 1,361 |

分组间 `F` 极差 0.042、`X` 极差 0.042，都小于 `δ`，没有截断、失败或未评判探针：运行间的噪声在它被比较的阈值之下。`off` 分组剩下的 `exact` 未命中也是真实遗漏，与 §3.1 相同。

### 3.3 决定

对某一类，满足 `F ≥ F_inherit − δ`、`X ≥ X_inherit − δ`、`V ≤ V_inherit`、失败不多于 `inherit` 的分组为通过；默认值是 `off`、`low`、`inherit` 中第一个在所有类上都通过的。规则按“所有类”写，这里不放宽：限制这次评估的是证据，所以 §13.4 的“覆盖”与 §2.1 说明哪些类贡献了数据，§1 说明这个决定的适用范围。

[实测] 在 OpenAI 兼容类上（`inherit`：`F` 0.958、`X` 0.958、`V` 0、失败 0）：

- `off`：`F` 0.972（`+0.014`，阈值 0.908）✓；`X` 1.000（`+0.042`）✓；`V` 0 ≤ 0 ✓；失败 0 ≤ 0 ✓ → 通过。
- `low`：`F` 0.958（`+0.000`）✓；`X` 1.000（`+0.042`）✓；`V` 0 ≤ 0 ✓；失败 0 ≤ 0 ✓ → 通过。
- `inherit` 作为自身通过。

第一个通过的取值是 **`off`**。对照类一致：`off` 在那里 `F` 1.000（`+0.042`）、`X` 0.958（`−0.042 ≥ −0.05`）、`V` 0、无失败，因此也通过。

### 3.4 是否引入设置

[实测] 在跑过的那一类上，`off` 通过了 §3.3 的非劣检验，且没有别的分组的 `F` 比它高出 `δ` 以上。因此**不引入**该设置：`off` 成为策略常量，并移除主分支上已有的 `compaction.json`。第二类推理未能运行（§2.3），Anthropic 预算式思考类未运行（§2.1），所以这条结论对跑过的那一类成立，对其他类是暂定的。

## 4. 第 2 阶段：目标长度

以 `--reasoning off` 运行。`S = min(α × O, β × B)` 向下取整到 100 的倍数，其中 `O` 是输出额度、`B = 窗口 − O`。对模型自身窗口的七个用例（`O` 8,192、`B` 1,040,384），在测试的取值下 `β` 从不约束，所以 `S(0.25, 0.05) = S(0.25, 0.10) = 2,000`，`S(0.5, 0.05) = S(0.5, 0.10) = 4,000`。`folding` 用例把窗口收窄到 8,000，于是 `O` 为 2,000、`B` 为 6,000，四条规则给出 300、500、300、600。

### 4.1 OpenAI 兼容类

[实测] 经过 §6 的人工纠正后：

| 分组 | F | X | V | C | 失败 | T 中位数 | T/S 中位数 | p90 T/S |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| 不写指令 | 71/72 = 0.986 | 24/24 = 1.000 | 0 | 0 | 0 | 459 | – | – |
| 0.25/0.05 | 71/72 = 0.986 | 24/24 = 1.000 | 0（原始 2） | 0 | 0 | 448 | 0.242 | 1.403 |
| 0.25/0.10 | 70/72 = 0.972 | 24/24 = 1.000 | 0（原始 2） | 0 | 0 | 464 | 0.232 | 1.074 |
| 0.50/0.05 | 71/72 = 0.986 | 24/24 = 1.000 | 0（原始 1） | 0 | 0 | 453 | 0.125 | 1.257 |
| 0.50/0.10 | 69/72 = 0.958 | 24/24 = 1.000 | 0（原始 2） | 0 | 0 | 487 | 0.132 | 0.777 |

每个分组相对最好的分组都通过：`F ≥ 0.986 − 0.05 = 0.936`（最低 0.958），`X ≥ 1.000 − 0.05 = 0.950`（每个都是 1.000），`V ≤ 0`。不写指令分组的 `C` 为 0、失败 0，不高于任何通过的目标分组（都是 0），因此**不保留指令**；没有目标被选中，p90 规则不适用。

### 4.2 对照第 2 阶段

对照的第 2 阶段度量的是端点的变化，不是摘要质量，也不进入任何决定。

[实测] 从 2026-10-28 16:04:06 UTC 起，端点无视 `thinking: {"type": "disabled"}`，返回不带签名的思考。该阶段的 178 条摘要请求中有 74 条以 “Model thinking is missing native continuation metadata” 失败：带思考的回复与失败的运行一一对应，且每个失败的运行只发出一条请求——读取器的错误不带失败事实，共享失败策略因此直接停止，不会重试。其余 104 条请求没有返回思考，正常完成。

[实测] 运行之后的一次探测（2026-10-29）向该端点发出两条一句话请求，一条声明关闭思考，一条以 1,024 token 的预算开启思考：两条回复都带思考、都不带签名。在那个状态下，发往该端点的每个请求都会在回复读取器里失败（`crates/dim-agent-aimux/src/stream.rs:261-273`），无论它请求什么推理取值。

[代码] 运行器调用的是产品策略，所以在那个状态下该端点上的压缩就是这样一个请求，会失败，结果记为 failed；读取器是所有请求共用的那一个，所以对话自己的回复也会以同样方式失败。用户看到的是 [ContextCompaction](../plugins/ContextCompaction.md) §5.8 的行为：自动压缩失败，请求在不压缩的情况下继续；恢复压缩失败则请求失败；手动压缩返回 `compaction_failed`。因此对照取自第 1 阶段，它在变化之前运行：161 条回复，没有一条带思考。

## 5. 计划大小的证据

[实测] 对 §4.1 的不写指令分组，每次运行的 `T` 对照该运行窗口上的计划 `replacement_size`：§13.3 的 `S`（α = 0.5、β = 0.10）加一个空的摘要包装，包装为 84 token。模型自身窗口上计划为 4,084 token，收窄的 `folding` 窗口上为 684。24 次运行中：

| 度量 | 值 |
| --- | --- |
| `T / 计划` 中位数 | 0.11 |
| `T / 计划` p90 | 0.67 |
| 超过计划的运行数 | 0 / 24 |
| 最大值 | 0.89（`folding` 的一次运行） |

除收窄的那个用例外，每个比值至多 0.20；p90 与最大值来自 `folding` 用例，其 600 token 的计划很小。超过计划不是致命的：§5.3 第 4 步会在提交任何内容之前，按替换内容的实际大小重新规划一次。

## 6. 人工纠正

记录决定之前，操作者阅读得分最低的摘要并手工纠正评判错误。每条纠正都是 `instructions` 中同一个 `absent` 探针：它的陈述不得作为现行规则出现；摘要把它作为初始、已取代的指令引用，评判把这次出现计为违规。共纠正 14 条判定，从 `present` 改为 `absent`：OpenAI 兼容第 1 阶段 3 条、对照第 1 阶段 4 条、OpenAI 兼容第 2 阶段 7 条。代表性引文：

| 运行 | 摘要引文 |
| --- | --- |
| OpenAI 兼容第 1 阶段，`inherit` | "The user initially said the runner could `unwrap` freely because it would never be called from production." |
| OpenAI 兼容第 2 阶段，0.50/0.05 | "**Initial instruction:** The user said the runner could use `unwrap` freely because it is a tool never called from production." |

## 9. 局限

- 评判与摘要同族。§13.4 要求在可能时使用不同家族；本次评估使用了同一家族，所以不能排除评判对自己家族的偏向。
- 只测了一类推理，即 OpenAI 兼容那类。OpenAI Responses 类被端点与驱动的组合阻塞（§2.3），Anthropic 预算式思考类在本次评估里没有模型（§2.1），所以跨类的结论只覆盖跑过的那一类：默认值对每一类都是 `off`，对没能运行的类是暂定的，等每一类能运行时规则在它上面重跑。
- 对照的无思考行为来自端点，在第 1 阶段的三个请求强度上成立。从第二阶段中途起，该端点对每个请求都返回不带签名的思考，所以该阶段不使用（§4.2）。
- 本处的 `X` 按修正后的运行器规则；早先按转义形式测得的读数低估了它。
