# 003：批准只管 agent 的决策

决策状态：提议。取代 [ADR 001“信任与跨语言调用”](../../adr/001-harness-foundation.md#trust-and-cross-language-calls)中关于项目 MCP 执行批准的部分，以及 AGENTS.md 第 11 条中对应的句子。ADR 001 其余内容不变。

## 背景

ADR 001 要求：项目里的 MCP 条目在启动 stdio 进程或连接 HTTP/SSE 之前，必须先有本机批准。批准绑定工作目录、服务 ID 和有效配置的指纹，存放在 `mcp-approvals.json`，通过 `mcp.approve` 和 `mcp.revoke` 管理。

插件设计随后要求其他“按配置运行东西”的功能也加同样的关卡：项目 Hook 命令、项目工作流定义、插件包。每个功能都要加自己的批准与撤销方法、列表里的批准状态、指纹和过期错误。这把两件不同的事混在了一起：

- Approval 与 Permission 决定 **agent 的决策**（模型的工具调用）能不能执行。
- 配置里写的命令之所以运行，是因为**配置这么写了**，不是 agent 决定的。它的安全由写配置、启用配置的人负责。

## 决策

### D1. Approval 与 Permission 只管 agent 的决策

Approval 与 Permission 作用于 agent 决定的动作，也就是模型的工具调用。这一点不变。对 MCP 服务的工具调用仍然像其他工具一样经过 Approval 与 Permission。

### D2. 配置引起的运行不需要本机批准

因配置而运行的命令和连接不是 agent 的决策，不需要批准：连接时启动的 MCP stdio 服务、MCP HTTP/SSE 连接、Hook 命令、工作流定义、插件包。启用了就运行。没有批准记录、没有配置指纹、没有批准状态，也没有批准和撤销方法。

### D3. 启用是普通配置；项目条目默认关闭

启用和禁用一个条目是普通配置，和批准无关。

- 来自项目来源（工作目录里的文件，例如 `.dimcode/`）的条目默认关闭。
- 项目文件不能启用自己的条目。项目条目的启用状态存放在用户本机配置里，按工作目录和条目 ID 区分，只能由用户通过该条目所有者的配置操作修改。
- 用户自己的配置不变：用户写的条目按用户写的启用。

因此，打开一个仓库时，在用户启用之前，不会运行仓库里的任何命令。

### D4. 接受的后果

用户启用一个项目条目后，项目文件里对它的命令或参数的后续修改（例如拉取新提交后）直接生效，不再询问。ADR 001 的指纹会要求重新批准。这一点接受：启用一个项目条目，就是信任该项目对这个条目的配置。这从来不是沙箱（ADR 001 已写明批准针对配置，不针对可执行文件内容）；操作系统隔离仍是单独的工作。

### D5. 不变的部分

宿主安全设置不进入 Timeline；重放、恢复或分叉都不会恢复或扩大权限。文件根授权与权限预设授予的东西和现在一样，不多也不少。

## 后果

- 删除 `mcp.approve` 和 `mcp.revoke`，调用返回 `unknown_method`。从 `mcp.catalog` 删除 `approval` 和 `approvalToken`。不再读取 `mcp-approvals.json`；已有文件被忽略，不迁移。原来有批准的项目条目在用户启用前处于关闭状态。
- 删除 CLI 的 `mcp approve` 命令。
- 插件设计（Hooks、Workflow、PluginManager 等）对项目来源的配置采用 D3，不加批准方法。
- AGENTS.md 第 11 条按本决策修改。
